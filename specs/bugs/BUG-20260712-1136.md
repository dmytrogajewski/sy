# BUG-20260712-1136: manual pin never actuates when the anti-thrash window is warm

## Summary
`sy power profile <arm>` is recorded as the tick's source label
(`pin:<arm>`) but the arm is dropped back to the rules baseline and
never actuated whenever an arm change happened within the last
`profile_thrash_min_interval_s` (30 s) — because `shield::project`
applies the anti-thrash `would_thrash` veto to operator pins.

## Reproduction
- Method: manual (live daemon) + hermetic unit test
- Test: `crate::power::shield::project::tests::forced_pin_bypasses_thrash_floor`
- Command (live):
  ```
  sy power profile flat-out      # inside 30 s of the previous switch
  sleep 5
  tail -1 telemetry-2026-07-12.ndjson
  ```
- Evidence (live):
  ```
  applied browse
  chain ['pin:flat-out','shield:COOL_AC','platform_profile: no-change',
         'epp: no-change','igpu: no-change','npu: no-change','cgroup: no-change']
  /sys/.../energy_performance_preference -> balance_power   (not performance)
  ```
  The source label is `pin:flat-out`, yet `applied_arm=browse` and every
  actuator is `no-change` — the pin was vetoed. When the baseline is
  stable for >30 s first, the same pin applies cleanly (`applied
  flat-out`, EPP -> `performance`), proving the anti-thrash floor is the
  blocker.

## Expected
An explicit operator pin (`sy power profile <arm>`) actuates on the next
tick regardless of how recently the arm last changed. The anti-thrash
floor exists to damp *bandit* oscillation, not to veto operator intent.

## Actual
`shield::project` walks the ranked candidate list (a singleton
`[pinned_arm]` when pinned) and, on `thrash.would_thrash(...) == true`,
`break`s out of the loop and returns the rules baseline. The pin is lost
for actuation even though the reason chain still records `pin:<arm>`.

## Root Cause
`src/power/shield/project.rs::project` treats every candidate — including
an operator pin — as subject to the `would_thrash` floor. The daemon has
no way to tell `project` that the top candidate is a forced pin that must
win. Manifests only when a prior arm change is <30 s old (e.g. rapid
`profile <arm>` / `profile --auto` toggling during debugging), which is
why it looked intermittent.

## Fix
Add `shield::project_forced` (delegates to a shared `project_inner` with a
`forced` flag). When `forced`, the anti-thrash `would_thrash` veto is
skipped so the pinned arm actuates; the SPEC §4 shield *safety*
constraints (Hot / BatteryLow / Meeting) still apply. `daemon::one_tick`
calls `project_forced` when a pin is set, `project` otherwise. The
bandit-flap suppression path is unchanged (regression-guarded by the
existing `rapid_flap_within_window_still_suppressed`).
