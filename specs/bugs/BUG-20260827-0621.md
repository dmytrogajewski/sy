# BUG-20260827-0621: Muse readiness rejected a capable GGUF route

## Symptom

The exact Muse Glimmer 30B Q4_K_XL artifact loaded on `dgx-spark`, but route publication failed closed. The original 1x1 opaque-black PNG was classified as `blue`; after correcting the image, the streamed tool probe exhausted 64 tokens and the pinned llama.cpp server rejected named-object `tool_choice` syntax.

## Root cause

The fixture was formally valid but below a useful perception-encoder resolution. Muse also opens reasoning unconditionally: `enable_thinking=false` is insufficient, and pinned llama.cpp commit `9ee9fc04c` cannot sampler-cap Muse because its parser does not register reasoning end tags.

## Fix

The signed generic vision policy now uses a deterministic 224x224 opaque-black PNG and a 256-token bounded response. The generic health adapter requests low reasoning strength, while the streamed protocol probe uses the portable `tool_choice: "required"` form, low reasoning, and 256 tokens. No repository, model name, or checkpoint branch was added to Rust.

## Evidence

The 224x224 fixture returned final content `black`. The exact pinned engine then streamed `capability_probe` with valid arguments, usage, and `finish_reason: "tool_calls"`. Managed generation 6 published successfully; stop and generation 7 restart retained engine fingerprint `sha256:bb384adc94255791dabf8631881d7a05c86f6a8f84b42c11814fa6ed7837849a` and artifact fingerprint `sha256:28b0eaab3ca8a1c1d9d039a37c32c430789127d566b1823d5b43318e59ffa836`.
