# BUG-20260829-1407: a completed stop can be durably reported as failed

## Summary

Stopping an exact managed generation can remove its container but leave the
operation durably failed when Docker reports a late removal error.

## Reproduction

- Stop the healthy Qwen3.8 candidate through `sy spark dgx-spark stop`.
- Observe operation `01M16K32BWZPMP52R5SE55C3WF` fail with
  `spark.instance.stop-failed`.
- Observe the exact generation absent on the next `ps` and reconcile scan,
  with no container, process, route, or GPU allocation remaining.
- Generation 19 reproduced the complementary timing window: operation
  `01M16QA19GJWR8SN4K47EQQ07G` failed at `12:18:32.833Z`, while the exact
  container did not finish stopping until `12:18:35.544Z` and remained as an
  exited, restart-disabled generation awaiting a second reap.
- Reconciliation then marked SQL state absent while retaining unresolved
  quarantine evidence. A later explicit stop took the clean-absent shortcut
  and left that exact stopped container in Docker, so doctor remained
  degraded even though user intent was stopped.

## Expected

The stop operation succeeds when an exact post-stop inspection proves that
the requested managed generation is absent. Model and compile-cache artifacts
remain retained.

## Actual

Any executor stop error immediately fails the durable operation without
checking whether the exact generation was removed before the late error.

## Root Cause

`run_stop` treats the stop RPC result as the final state. Docker stop and
remove are separate calls, so a successful state transition followed by a
benign remove race is indistinguishable from a failure at the agent boundary.

## Fix

After a stop RPC error, inspect the same instance ID and generation through
the privileged executor. Treat an authoritative absent result as success. If
the exact generation is still running, poll only within the requested stop
deadline; once it is stopped, retry the same exact-generation removal once.
A still-running generation at the deadline or failed inspection preserves the
existing failure behavior.

The clean-absent shortcut is valid only when quarantine evidence is empty. An
absent generation with unresolved quarantine still executes the same
exact-generation stop, while unrelated or identity-mismatched containers
remain untouched.

## Traceability

- Regression: agent/executor protocol test where stop removes the exact
  generation and then reports an error.
- Regression: agent/executor protocol test where the failed stop remains
  running for one inspection, then becomes stopped and is reaped on the second
  exact-generation stop.
- Black-box regression: ordinary clean absence performs no executor removal,
  while absent state plus unresolved quarantine performs exactly one
  exact-generation removal.
- Real-device acceptance: the same stop/start cycle succeeds without direct
  Docker lifecycle mutation and leaves no orphan container or process.

Generation 20 satisfied the real-device acceptance through managed stop
operation `01M16SJQDHABTR0M7B4CTJ1759`: the operation succeeded, the exact
generation became absent, and no matching container or process remained.
Generation 21 then exercised bounded serve cancellation through operation
`01M16SKENAT8JVNSAC1APNB0NA`; its partially created exact generation was also
reaped without an orphan.
