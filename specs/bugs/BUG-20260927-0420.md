# BUG-20260927-0420: on-demand workloads could never run while the daemon was up

## Summary

`sy aiplane run --workload stt` (and `ocr`, `vad`) answered
`sy-aiplane worker not reachable` with **zero** log lines whenever the aiplane
daemon was running. The same command succeeded with the daemon stopped,
because the CLI's documented daemon-down fall-through ran the workload
in-process. On-demand kinds were therefore reachable only in the one
configuration nobody uses in production, and `tests/workload_stt.rs` — which
black-boxes the CLI — had been exercising that fall-through for its whole
life, so CI never saw the gap.

## Reproduction

```bash
systemctl --user is-active sy-knowledge.service          # active (daemon up)
sy aiplane run --workload stt --json --in-file /tmp/stt_input.json
# error: daemon: Internal: sy-aiplane worker not reachable
journalctl --user -u sy-knowledge.service | grep 'kind":"stt'   # nothing
```

## Expected

`Supervisor::run_batch` serves any registered kind, spawning the worker if the
warm set (`embed`, `rerank`) does not contain it — the same contract the
in-process path offers.

## Actual

`Supervisor::run_batch` called `socket_for(kind)?` and connected straight to
`/run/user/1000/sy-aiplane-worker-stt.sock`. For a kind outside the warm set
nothing had ever bound that socket: `socket_for` happily returns the
deterministic path whether or not a `ManagedChild` exists, so the connect
failed and the supervisor never consulted its own spawn path. No worker was
forked, so there was nothing to log.

## Root Cause

`ensure(kind)` (spawn-if-absent, then poll Health to `Ready`) is the only
entry point that raises a worker, and it was called exclusively from the
startup warm-set loop and `Supervisor::restart`. `run_batch` predates the
warm-pool refactor and assumed its caller had already ensured the kind. The
daemon-side `aiplane.run` bridge passes whatever the client asked for, so the
assumption silently broke for every kind not named in `warm_models`.

## Fix

`src/aiplane/supervisor/mod.rs::run_batch` now raises before it connects:

```rust
self.ensure(kind, WORKER_RAISE_DEADLINE)?;
let socket = self.socket_for(kind)?;
```

`WORKER_RAISE_DEADLINE` (900 s) is a named constant because it has to cover
the slowest legitimate load, not just the warm ones. `ensure` is idempotent —
for `embed`/`rerank` it is a pool touch plus one Health probe.

## Verification

Red first: `aiplane::supervisor::tests::run_batch_raises_a_kind_outside_the_warm_set`
drives `run_batch(WorkloadKind::Stt, …)` against a `FakeSpawn` that only
binds the socket it is handed, reproducing the production error verbatim;
green after the two-line change.

Production check after installing the fix (`.rai` cache present, see
BUG-20260927-0910 for why that matters):

```text
09:06:12 worker starting kind=stt pid=1691259
09:06:19 worker ready    kind=stt backend=vitisai
sy aiplane run --workload stt → exit 0 in 10.9 s, transcript correct
```

## Follow-ups (not in this fix)

- `ocr` and `vad` are still unimplemented stubs; they now fail with
  "model not prepared" from inside the worker instead of a phantom
  reachability error, which is the honest signal but not a feature.
- A caller-facing "loading, retry in Ns" response would beat a blocking
  `run_batch` for cold kinds; the raise deadline currently absorbs the wait.
