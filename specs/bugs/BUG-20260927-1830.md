# BUG-20260927-1830: `sy knowledge index` had no way to reach the NPU

## Summary

`sy knowledge index [--source X]` and `sy knowledge bench` failed with
`embed batch: aiplane supervisor not running` whether the plane was up or
down, because the batch embed route only ever looked for an *in-process*
supervisor — which no CLI process installs — while the daemon had been
advertising the batched `aiplane.batch` method all along.

## Reproduction

- Method: manual, plane healthy.
- Command: `sy knowledge index --source ~/knowledge --json`
- Evidence:

  ```text
  Error: embed batch: aiplane supervisor not running
  ```

  `sy doctor` reports `pass=21 fail=0` at the same moment, and
  `systemctl --user show sy-knowledge -p NRestarts` reads `0`: the plane is
  fine, the CLI just has no road to it.

## Expected

`sy knowledge index` is documented as a one-shot incremental pass that
"talks to Qdrant directly". Embedding has to happen somewhere, and per the
one-process-per-NPU rule that somewhere is the daemon — the CLI must not open
a second ORT session on `/dev/accel/accel0`, which is single-context.

## Actual

`knowledge::embed::embed_batch` asked `supervisor::current()`, which only
`knowledge::daemon.rs` ever installs, and errored otherwise. Three consequences:

1. With the daemon up: hard failure, no delegation — even though
   `AIPLANE_METHODS` already advertises `aiplane.batch` and
   `Handler::handle_aiplane_batch` already runs `AiplaneDispatch::batch`
   behind a cancel-registration guard. The wire surface existed; the client
   side of it never got written.
2. With the daemon down: the same failure, so the documented
   "works without the daemon" promise was false in both directions.
3. `sy knowledge bench` (which calls `embed_batch` in 64-text groups) was
   equally dead, so the very command for measuring embed throughput could
   not run.

## Root Cause

`embed_one` (the search path) learned to reach the daemon early, so the batch
path's own docstring — "routes through the embed worker via one batched IPC" —
described an intent the code never implemented. `require_supervisor()` turned
that gap into a one-line error that reads like an internal invariant rather
than an operational condition.

## Fix

1. **Client side of `aiplane.batch`** (`aiplane::ipc::batch_blocking`): v1
   envelope with the caller's QoS class, framed request, decoded
   `{ "outputs": [...] }`. Three guards pinned by tests — the params must keep
   deserializing into the server's own `AiplaneBatchParams` struct; a short
   output list is an error, because the index path maps `vector[i] → chunk[i]`
   positionally and a truncated batch would half-index a file and call it
   done; a missing socket says `aiplane daemon not running: <path>`.
2. **Route by device ownership** in `embed_batch`: this process is the plane →
   in-process supervisor; otherwise → IPC in `EMBED_IPC_MAX_CALL = 64`-sized
   groups. There is deliberately no local-embed third route (that is how
   `BUG-20260927-0910`'s 19.5 GiB CPU-EP storm was born). The 64 cap was
   written as a shield for the fact that `aiplane.batch` bypassed the
   scheduler's per-class admission — one giant batch would park a 25 MB
   export's whole chunk list on the NPU and starve a foreground
   `knowledge_search`. **That bypass is since fixed** (BUG-20260927-2010):
   batches are admitted by class, and the cap now only bounds one request's
   payload and its preemption waste.
3. **Actionable failure**: with no plane, the message now carries
   `systemctl --user start sy-knowledge.service` instead of an internal
   invariant.
4. **Told the truth in `--help`**: `KnowledgeCmd::Index` now states that Qdrant
   writes happen in this process but embedding always runs on the plane's
   worker.
5. **Closed the env-lock hole the new tests stepped on.** Adding two
   env-mutating tests surfaced a latent flake:
   `aiplane::ipc::tests::aiplane_cancel_resolves_workload_from_inflight_registry`
   bound its listener under one `XDG_RUNTIME_DIR` and connected under another
   (`ENOENT`), then poisoned `TEST_ENV_LOCK` for the STT test behind it. The
   contract in `src/aiplane/mod.rs` says every env-touching test in this
   binary rendezvouses on `TEST_ENV_LOCK`, and `ipc_cli::tests::with_runtime_dir`
   plus `mon::cli`'s snapshot test each held a *private* mutex instead — which
   serialises against nothing. Both now take the shared lock, and the new tests
   here avoid the global entirely (`batch_blocking_at` takes the socket path;
   `plane_unreachable` is asserted as a pure message), so they cannot perturb a
   smoke test's bind. Verified with two consecutive full runs: 1520 tests,
   0 failures each.

## Traceability

- Failing commands: `sy knowledge index --source <path>`, `sy knowledge bench`.
- Fixed in: `src/aiplane/ipc.rs` (`batch_blocking`, `batch_params`,
  `decode_batch_outputs`, `v1_request_with_priority`, `BATCH_READ_TIMEOUT`),
  `src/knowledge/embed.rs` (`embed_batch`, `EMBED_IPC_MAX_CALL`,
  `vectors_from`), `src/knowledge/mod.rs` (`Index` docstring),
  `src/ipc_cli.rs` + `src/mon/cli.rs` (shared env lock), `CHANGELOG.md`.
- Tests: `aiplane::ipc::tests::{batch_params_match_the_server_params_struct,
  batch_outputs_decode_and_enforce_length,
  batch_blocking_reports_a_missing_daemon_with_the_socket_path}`,
  `knowledge::embed::tests::{embed_batch_without_a_plane_names_the_fix,
  vectors_from_keeps_positional_order_and_rejects_other_variants}`.
- Verified live: `sy knowledge index --source /tmp/sy-proof --json` →
  `{"scanned":1,"indexed":1,"skipped":0,"deleted":0,"elapsed_ms":261}`;
  `sy knowledge bench --json` → 256 chunks, 33.0 chunks/s, mean 64-chunk
  batch 1939 ms (hence the 120 s read budget, ~60× headroom); deleting the
  source and re-running the pass made the daemon log `deleted: 1`, leaving no
  orphan points (`file_path` scroll returns 0), `sy.toml` byte-identical to
  its pre-experiment copy, and the collection back at its 115 522 points.
- Follow-up this exposes, not taken: `aiplane.batch` runs outside the
  scheduler, so it neither admits by QoS class nor respects
  `queue_caps`. A scheduler-aware batch (or an admission check on the
  daemon side) is the honest version of item 2 above.
