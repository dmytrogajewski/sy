# BUG-20260927-0910: whisper's cold VAIP compile ran inside `MemoryHigh=12G` and throttled to a permanent stall

## Summary

Once `run_batch` learned to raise on-demand kinds (BUG-20260927-0420), the STT
worker spawned, bound its socket, reported `loading`, and never reached
`Ready`: `worker stt did not become Ready within 900s`. It was not compiling
slowly. The kernel had it pinned in direct reclaim — the `sy-knowledge.service`
cgroup is capped at `MemoryHigh=12G` while a cold `whisper-medium` VitisAI
compile peaks at **19.5 GB**. `sy doctor`'s coredump warning and the four-day
knowledge outage were neighbours of this bug but not this bug.

## Reproduction

```bash
sy aiplane run --workload stt --json --in-file /tmp/stt_input.json   # daemon up
# daemon: Internal: workload failed: worker stt did not become Ready within 900s
```

## Expected

Either the load finishes, or it fails fast with an actionable message. The
NPU plane must not be able to park itself in uninterruptible sleep.

## Actual

| observed while "compiling" | value |
|---|---|
| worker state | `loading` (never `ready`) |
| CPU | ≈ 0 % (3.5 % lifetime average) |
| thread wchan | `__mem_cgroup_handle_over_high` on 3 of 9 threads |
| cgroup `memory.current` / `memory.high` | 14.0 GB / **12.0 GB** |
| cgroup `memory.events high` | 347 871 |
| cgroup `memory.pressure full avg10` | 70 % |
| host free | 35 GB available — the box was *not* out of RAM |
| swap | 8.0 GB / 8.0 GB used |

`MemoryHigh` exceeded means the kernel charges every further fault and
throttles the offending cgroup by up to 100 ms per fault, scaling with how far
over the limit it is. The compile needed ~8 GB more than it was allowed, so
the throttle never backed off: utime advanced by 5 ticks in 5 s. A
`systemctl --user stop` on the unit then blocked until `WatchdogSec` fired and
left the unit `failed`, because the throttled threads were in `D` state and
could not take SIGKILL.

## Root Cause

Two design gaps meeting:

1. **The runtime cgroup was sized without ever having measured a cold
   compile.** `configs/systemd/user/sy-knowledge.service` carries
   `MemoryHigh=12G` with the rationale "aiplane warm-pool + qdrant working set
   + the fastembed BPE vocab all together fit comfortably under 12 GiB" —
   stale twice over: qdrant has run in its own `sy-qdrant.service` since
   arch-supervision Step 6, and aiplane workers are *children of the knowledge
   daemon*, so they all share this one cgroup. Whisper was never in the
   arithmetic.
2. **The AIE compile was deferred to the worst possible moment.**
   `prep_npu_workload.py --workload stt` only downloads and copies: its
   comment claims the upstream ONNX is "already VAIML-partitioned", which is
   true of the *graph* and false of the *binary* — the `.rai` AIE bitstream
   still has to be produced locally. embed and rerank warm that cache at prep
   time through `warm_npu_cache()`; the prebuilt-ONNX branch returns early and
   skips it. So the first `aiplane run --workload stt` after any cache sweep
   (see BUG-20260927-0119: the disk strategy had pruned `whisper-medium/`)
   paid the whole compile inside the capped, `Nice=10`,
   `IOSchedulingClass=idle` runtime cgroup.

Measured cost of that compile, run uncapped in a transient scope:

```text
Elapsed (wall clock) time: 6:01.61      Exit status: 0
Maximum resident set size: 13.9 GB      cgroup memory.peak: 19.5 GB
artefacts: whisper_medium_encoder.rai 359 MB, whisper_medium_decoder.rai 527 MB
```

## Fix

Move the compile to prep time and make the worker refuse to attempt it:

1. `scripts/prep_npu_workload.py` — the prebuilt branch now warms both
   whisper partitions through the existing `warm_npu_cache()` (encoder and
   decoder, with the same `cache_key`s the loader uses), still skippable with
   `--skip-warm`. Prep owns the 6-minute compile in the login cgroup, exactly
   like embed and rerank already do.
2. `src/aiplane/workloads/stt.rs` — before creating either session, require
   the compiled partition (`<cache_dir>/<cache_key>/*.rai`) and otherwise bail
   with the prep command. A missing cache is now a two-line error instead of a
   20 GB stall. New pure helper `vaip_partition_compiled` is unit-tested
   hermetically under a temp `HOME`.
3. `configs/systemd/user/sy-knowledge.service` — `MemoryHigh=16G`, sized from
   the measured warm peak (10.1 GB cgroup: embed 2.2 GB + rerank 2.0 GB + stt
   5.2 GB RSS + model page cache), and the rationale rewritten to say so.
   `tests/knowledge_unit_memory_high_covers_worker_peak.rs` pins the floor.
4. `aiplane run`'s in-process path now routes the AIE compiler's `stdout`
   chatter to `stderr` (fd-level `dup2` guard) so `--json` stays parseable —
   the cold run above emitted 7 MB of banner text into the JSON document.

## Verification

- Warm STT through the daemon, `.rai` present: `worker ready` at +7 s,
  cgroup peak 10.1 GB, `memory.events high 0`, exit 0, transcript exact:
  "He hoped there would be stew for dinner, turnips and carrots and bruised
  potatoes and fat mutton-pieces to be ladled out in thick, peppered,
  flour-fattened sauce."
- `memory.events high` stays 0 with three workers resident, where before it
  climbed by ~20 k per five minutes.
- Gated: `cargo test --features test-npu --test workload_stt`.

## Follow-ups (not in this fix)

- Workers should live in per-kind transient scopes so one workload's footprint
  cannot throttle another; the supervisor tracks `std::process::Child` handles
  today, so this needs a pid-liveness substitute — deliberately out of scope.
- `run_batch` should answer "loading, retry in Ns" instead of absorbing the
  wait, and the 900 s `WORKER_RAISE_DEADLINE` should then shrink accordingly.
- The 12 G→16 G cap still assumes at most one heavy cold load at a time; a
  `MemoryHigh` per kind is the real fix (previous bullet).
