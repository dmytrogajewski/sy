# BUG-20260712-1201: MEETING shield state is absorbing — never releases after the call ends

Related: **BUG-20260712-1200** (`call_active` one-tick pulse). Same
call-detection path, fixed as one change. The release logic here depends
on `call_active` being a faithful level, which 1200 restores; without
1200 the DFA never even saw the call long enough to matter, and with the
old absorbing DFA the pulse still latched MEETING forever.

## Summary
`src/power/shield/dfa.rs` — `transition()` pinned MEETING with
`if call_active || prev == ShieldState::Meeting { return Meeting; }`.
Once MEETING was entered it persisted until daemon restart: the
`prev == Meeting` disjunct is self-sustaining and nothing ever cleared
it. The config already promised a release —
`meeting_lock_after_vad_s = 30` (`~/.config/sy/power.toml`,
`ShieldConfig`) — but that field was defined and never read anywhere in
the DFA or daemon.

## Reproduction
- Method: live host probe (2026-07-12) plus source trace.
- Command: `systemd-inhibit --what=idle --who=zoom sleep 20`.
- Observed: a 20 s inhibitor latched shield state MEETING for >5 min
  (until the probe ended), clamping the applied arm to `call` the whole
  time. No return to COOL_AC/WARM_AC ever occurred.
- Source trace: `dfa.rs:89` `prev == ShieldState::Meeting` re-returns
  MEETING every tick regardless of `call_active`, and no caller reset
  `prev`. `meeting_lock_after_vad_s` had zero readers (`grep` confirmed
  it was defined in `config.rs` and asserted in a config test only).

## Expected
Per sy-power ROADMAP Step 5 R1 + SPEC §4: MEETING is held while
`call_active` is true (level, per BUG-20260712-1200) and for
`meeting_lock_after_vad_s` seconds after `call_active` last went false,
then the DFA re-evaluates the thermal/battery/idle rungs normally.
MEETING is NOT an absorbing state.

## Actual
MEETING absorbed: entered on the first `call_active` tick, held forever.
The `call` arm was clamped for the rest of the daemon's life.

## Root Cause
The DFA's MEETING branch had no release condition. The "30 s lock after
VAD release" timer that the docstring and `meeting_lock_after_vad_s`
promised was never implemented — neither in the DFA nor in the daemon.

## Fix
`transition` takes a new injected input `secs_since_call: Option<f32>`
(seconds since `call_active` was last true; `None` ⇒ never seen this
run). MEETING is now held only while
`call_active || (prev == Meeting && secs_since_call < meeting_lock_after_vad_s)`.
Once the lock window elapses the DFA falls through to the normal
thermal/battery/cool rungs. The DFA stays pure — the elapsed time is an
argument, not a wall-clock read. The daemon threads it via a new
`ShieldTickState { prev, last_call_at }` (replacing the bare
`&mut ShieldState` in `one_tick`): each tick it stamps `last_call_at =
snap.ts` when `call_active` is true, then computes
`secs_since_call = snap.ts - last_call_at`. Because the timestamp comes
off the injected clock, the daemon path stays hermetic under `MockClock`.

## Tests (`src/power/shield/dfa.rs`)
- `meeting_releases_after_lock_window` — call goes live (MEETING), then
  `call_active=false`; held at `meeting_lock_after_vad_s - 1` s, RELEASES
  to COOL_AC at `meeting_lock_after_vad_s` s. FAILS on the old absorbing
  code (MEETING was permanent).
- `meeting_held_within_lock_window` — MEETING stays pinned for every
  second inside the window (no premature release).
- `full_transition_table` and the other DFA rungs updated for the new
  4-arg signature and stay green.
