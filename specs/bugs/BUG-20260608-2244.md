# BUG-20260608-2244: sy-powerd panics on boot — "Cannot start a runtime from within a runtime"

## Summary
`sy-powerd` aborts during startup because the PPD D-Bus owner probe
(`zbus::blocking`) runs on the daemon's tokio runtime thread, tripping
tokio's nested-runtime guard — so the power plane has been crash-looping
and learning nothing since the binary was reinstalled on 2026-06-06.

## Reproduction
- Method: test + manual
- Test: `src/power/intent/logind.rs::tests::new_does_not_panic_inside_tokio_runtime`
  — constructs `LogindChannel::new` inside a `current_thread` tokio
  runtime (what `build_live_intent` does). With the `tokio` backend it
  panics with the production message; with `async-io` it passes.
- Command (manual): `RUST_BACKTRACE=full ./target/debug/sy power daemon`
- Evidence:
  - `systemctl --user status sy-powerd.service` → `failed (Result: exit-code)`,
    `status=101`, `Start request repeated too quickly` (hit the restart limit).
  - Journal / crash records (`~/.local/state/sy/power/crash/`):
    ```
    thread 'main' panicked at tokio-1.52.1/.../multi_thread/mod.rs:91:9:
    Cannot start a runtime from within a runtime. This happens because a
    function (like `block_on`) attempted to block the current thread while
    the thread is being used to drive asynchronous tasks.
    ```
  - Crash-file counts confirm a continuous loop after the 2026-06-06 reinstall:
    Jun 5 = 10, Jun 6 = 6, Jun 7 = 30, Jun 8 = 26.
  - Last clean shutdown / learned state: `checkpoint.json` dated 2026-05-29
    23:44; no `telemetry-*.ndjson` written since (the panic fires before the
    1 Hz tick loop, so no sensors are read and no bandit updates happen).

## Expected
`sy power daemon` binds its IPC + metrics sockets, signals `READY=1`, and
enters the 1 Hz sensor/intent/telemetry tick loop, learning continuously.
The optional PPD D-Bus shim binds (or degrades to observer mode) without
affecting the critical path.

## Actual
The daemon binds both sockets, logs `ready`, then panics ~100 ms later on
the main thread and exits 101. systemd restarts it 5×/25 s, then gives up
("start request repeated too quickly"). The plane is down; no learning.

## Root Cause
**Primary (regression):** commit `f99f99b` ("save", 2026-05-30 16:18)
added the `tokio` feature to the workspace `zbus` dependency
(`Cargo.toml`), so the resolved set became `blocking-api + async-io +
tokio`. zbus's `utils::block_on` is compile-gated: with `tokio` present it
builds a cached **multi-thread** `tokio::runtime::Runtime` and `block_on`s
it (`zbus-5.15.0/src/utils.rs:52`) instead of using the runtime-agnostic
`async-io` backend. The power daemon (`daemon.rs::run`) drives a
`current_thread` tokio runtime via `rt.block_on(run_async())`
(unchanged since `5b8bdbc`). The first `zbus::blocking` call on that
thread — `LogindChannel::new` → `zbus::blocking::Connection::system()`
(`intent/logind.rs:155`, reached from `build_live_intent`,
`daemon.rs:1325/1660`) — therefore tries to start a tokio runtime inside a
tokio runtime and aborts with status 101. `MprisChannel`, `ScreenCastChannel`,
and `NotifyChannel` (also `zbus::blocking`) and the PPD shim's owner probe
would hit the same wall; logind just constructs first. Timeline confirms:
last clean checkpoint 2026-05-29, crash loops begin 2026-05-30 (the
feature-flip day), continuous after the 2026-06-06 binary reinstall.
mundy (via iced) already requests zbus's `async-io`; `f99f99b` stacked
`tokio` on top, and zbus prefers `tokio` when both are present. The same
wall applies to `MprisChannel`, `ScreenCastChannel`, `NotifyChannel`, and
the PPD shim's owner probe — every `zbus::blocking` site on the daemon
runtime thread — so the fix targets the backend, not any single call site.

## Fix
Switch the `zbus` feature set from `["blocking-api", "tokio"]` to
`["blocking-api", "async-io"]` (`Cargo.toml`). `async-io`'s `block_on` is
runtime-agnostic, so every `zbus::blocking` call (logind, mpris, portal,
notify, ppd-shim) is safe on the daemon's runtime thread, and the one
async user (`file::fs::mounts`, `zbus::Connection::system().await`) runs
on zbus's own async-io reactor. `cargo tree -e features` confirms `tokio`
is no longer enabled on zbus and resolution agrees with mundy's
`async-io`. Single-line dependency change; no source edits to the intent
channels or the shim.

## Verification
- `./target/debug/sy power daemon` boots: logs `sy-powerd listening`,
  `power mon-exporter bound`, `checkpoint hydrated`, `PPD shim bound`, and
  runs the 1 Hz tick loop (no panic). Foreground `actuator failed` /
  NPU-lever-disabled lines are expected without the unit's polkit +
  capabilities and are not regressions.

## Traceability
- Failing test: `src/power/intent/logind.rs::tests::new_does_not_panic_inside_tokio_runtime`
- Fixed in: `Cargo.toml` (workspace `zbus` dependency: `tokio` → `async-io`)
