# BUG-20260827-0332: Hub tree drops LFS SHA during strict artifact planning

## Summary

Selective catalog download rejects a correct immutable GGUF because the current Hugging Face tree payload calls the LFS SHA-256 `oid` while the pinned client model expects `sha256`.

## Reproduction

- Method: real-device dry-run plus unit test.
- Test: `src/spark/model.rs::tests::linked_etag_recovers_missing_tree_lfs_sha256`.
- Command: `sy spark dgx-spark download qwen3.8:27b --dry-run --json`.
- Evidence: exit `3`, `artifact selection does not match the immutable Hub tree`; the pinned tree reports the exact configured size and `lfs.oid`, but deserialization leaves `BlobLfsInfo.sha256` empty.

## Expected

The planner independently obtains and verifies the selected file's LFS content SHA-256 without weakening the immutable catalog check.

## Actual

The catalog SHA was compared with `None`, causing a policy rejection before download.

## Root Cause

The Hub's expanded tree currently emits the LFS content digest as `lfs.oid`; `hf-hub` 1.0.0's `BlobLfsInfo` expects a `sha256` field, so serde discards the digest. The top-level tree `oid` is the Git pointer object and cannot verify payload bytes.

## Fix

For only the explicitly selected files whose tree digest is absent, the planner sends an authenticated, no-redirect `HEAD` request to the immutable resolve URL. It prioritizes `X-Linked-ETag`, which is the LFS payload SHA-256, and checks the linked size before retaining the digest. Invalid/non-SHA ETags remain unset and strict catalog matching still fails closed.

## Traceability

- Failing test: `src/spark/model.rs::tests::linked_etag_recovers_missing_tree_lfs_sha256`
- Fixed in: `src/spark/model.rs`
