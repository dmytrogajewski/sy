# BUG-20260927-0316: search advertises ids that resolve to no point, so `knowledge_get_chunk` always returns null

## Summary

`knowledge_search` carries a `chunk_id` that its own `knowledge_get_chunk`
cannot resolve — 0 of 4 sampled ids matched the point qdrant actually
stores, and every fetch answered `{"chunk": null}`. The drill-down step of
REQ-10 (bounded search → fetch full chunk) was dead for the whole 115k-point
corpus, silently. Found while verifying the plane after BUG-20260927-0119:
the applet was up, indexing, and reranking, so every health surface said
healthy while the second half of the agent-facing API returned nothing.

## Reproduction

```bash
# 1. Ask the MCP surface for a hit and keep its advertised id.
printf '%s\n' \
 '{"jsonrpc":"2.0","id":1,"method":"initialize","params":{"protocolVersion":"2024-11-05","capabilities":{},"clientInfo":{"name":"v","version":"0"}}}' \
 '{"jsonrpc":"2.0","method":"notifications/initialized","params":{}}' \
 '{"jsonrpc":"2.0","id":2,"method":"tools/call","params":{"name":"knowledge_search","arguments":{"query":"Лу контейнеры офис","limit":4,"rerank":false}}}' \
 '{"jsonrpc":"2.0","id":3,"method":"tools/call","params":{"name":"knowledge_get_chunk","arguments":{"chunk_id":"<id from step 2>"}}}' \
 | sy knowledge mcp
# 2. Compare that id against the point qdrant stores for the same chunk:
curl -s -X POST localhost:6333/collections/sy_knowledge/points/scroll \
  -H 'Content-Type: application/json' \
  -d '{"limit":3,"with_payload":["file_path","chunk_index"],
       "filter":{"must":[{"key":"file_path","match":{"value":"/home/dmitriy/knowledge/telegram/result.json"}},
                        {"key":"chunk_index","match":{"value":990}}]}}'
```

Observed (2026-09-27 03:08): advertised `ca6f42ec-…`, stored
`92ddfcba-…` for the same chunk; 4/4 sampled chunks disagreed.

## Expected

`knowledge_get_chunk(knowledge_search(...).results[i].chunk_id)` returns that
chunk's full text, as the tool description promises.

## Actual

`{"chunk": null}` for every hit. Secondary finding: `sy knowledge search
--json` omits `chunk_id` entirely (keys were `score`, `file_path`,
`chunk_index`, `chunk_text`), so the CLI gave no way to notice or use the id
while the MCP tool advertised a broken one.

## Root Cause

The daemon **re-derived** the identifier instead of returning the one qdrant
handed back. `SearchHit` (qdrant's search response) never even deserialized
the `id` field, so both `HitRow` construction sites did:

```rust
chunk_id: crate::knowledge::chunk::point_id(&h.payload.file_path, h.payload.chunk_index)
```

That is a different key than the one the point was written under. Pipelines
hash their own domain key, not the payload metadata:

- `pipeline/telegram.rs:101` — `point_id(key, anchor.id)` where `anchor.id`
  is the **Telegram message id**, while the payload's `chunk_index` is the
  **window ordinal** (`idx`), a strictly different number;
- `pipeline/telegram.rs:193` — media chunks hash a `media_key` with index 0.

So for every windowed telegram chunk both arguments were wrong, and the
derived id named a point that does not exist. `get_point()` asked qdrant for
a nonexistent id, `result: []` came back, and `Ok(None)` was reported as a
legitimate "unknown id" — the failure was shaped exactly like a normal miss,
which is why it survived while the corpus grew to 115k points.

## Fix

1. `qdrant::SearchHit` now deserializes qdrant's `id` (tolerant of both the
   UUID strings we upsert and unsigned-integer ids), and both `HitRow`
   construction sites pass it through verbatim. The id is authoritative at
   the source, so it is immune to per-pipeline key conventions and to any
   future `point_id` change.
2. `sy knowledge search --json` emits `chunk_id` alongside the MCP tool, so
   CLI and agent surfaces agree and the round trip is testable from a shell.
3. Unit test `knowledge::qdrant::tests::search_hits_carry_qdrants_own_point_id`
   locks the deserialization (string + numeric id shapes).

## Follow-ups (not in this fix)

- Retrieval *quality*, not availability: the largest source indexes
  ~2 000-character message windows, and mean-pooled E5 base vectors for
  multi-topic windows collapse into a flat 0.81–0.84 similarity band, so a
  query that names one sentence inside such a window cannot outrank it
  (a verbatim short chunk still ranks #1 at 0.93 with clear separation).
  Smaller windows or overlapping windows would move the band; measured via
  `--no-rerank` score distributions, not guessed.
- The corpus predates this fix, so ids written by older pipelines stay
  whatever they are; the fix makes them *readable* rather than rewriting
  them. No re-index is required.
- `pipeline/telegram.rs` could store the anchor message id in the payload so
  a hit's metadata explains its own id; the fix no longer depends on it.
- The corpus indexes near-empty chunks: hits with `chunk_text` of 0–9
  characters (`"-"`, `"("`) from telegram video/media files occupy real
  points and win ANN ties against actual content. Skipping chunks below a
  token floor at pipeline level would return that space to real text.
  Verified through MCP `knowledge_search`, not inferred.
