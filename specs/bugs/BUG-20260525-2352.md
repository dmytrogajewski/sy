# BUG-20260525-2352: trainer corpus collected during 14-day onboarding has zero `call` + zero `build` rows; the day-14 GRU lands with 2 of 5 softmax classes never observed

## Summary
The trainer (`src/power/trainer.rs::retrain_gru`) reads `applied_arm` from each NDJSON row and projects it onto a 5-class taxonomy `[idle, browse, call, code, build]` via `arm_to_class_idx` (`trainer.rs:425-435`). During the 14-day onboarding window the daemon refuses bandit picks (`evaluate_retrain_trigger`, gated on `!onboarding_active`) and falls back to `rules_baseline` (`src/power/policy/rules.rs:29`), a deterministic 5-state map: `cool_ac=browse`, `warm_ac=code`, `hot=idle`, `battery_low=whisper`, `meeting=call` (per `configs/sy/power.toml:[rules_baseline]`). The `meeting` shield state is only entered when `intent::mpris` or `intent::portal` detects an active call; on this host neither has fired in 6 days → 0 `call` rows. The `build` / `flat-out` / `npu-burst` arms are NEVER picked by the rules baseline (they don't appear in the `[rules_baseline]` map at all) → 0 `build` rows. Concretely across all 6 collected telemetry files (262,786 rows):

| arm in audit log | rows | trainer class | trainer class share |
|---|---|---|---|
| browse | 219,690 | browse | 83.6% |
| idle | 27,068 | idle | 10.3% (with whisper) |
| whisper | 4,610 | idle | (folded) |
| code | 11,404 | code | 4.3% |
| call | **0** | **call** | **0%** |
| build / flat-out / npu-burst | **0** | **build** | **0%** |

When `retrain_gru` fires on day 14 (or earlier via the drift-driven path), it trains a 5-way softmax head on a corpus that has never seen `call` or `build` exemplars. The hand-rolled SGD will drive those classes' head weights toward zero (no gradient signal); the resulting GRU will assign ~0 probability to `call` and `build` for every input. The validation gate (`trainer.rs:848-873`) checks argmax accuracy only, so the model trivially scores ~84% by always predicting `browse` and ships clean. The bandit's CLUCB context vector will then ingest a forecast distribution that's structurally incapable of suggesting `call` or `build`, biasing arm selection back toward whatever the rules baseline picked — a stable but degenerate equilibrium that defeats the entire ML plane.

## Expected
1. The trainer refuses to ship a model whose training corpus has any class with zero exemplars. Returns `TrainerError::InsufficientClassCoverage { missing: Vec<&'static str> }`.
2. OR: the trainer ships a smaller model — `n_classes = number-of-observed-classes` — and the validation gate enforces minimum per-class recall (e.g. ≥ 0.5 on every observed class).
3. The daemon's reaction to `InsufficientClassCoverage` is to stay on the rules-baseline / shipped warmup ONNX and surface the gap on `sy power status` (`model.version_sha = "rules-baseline (insufficient class coverage: call, build)"`).

## Actual
1. Trainer happily ships a 5-class model trained on 3 classes (idle/browse/code, with whisper folded into idle).
2. Validation gate only checks argmax accuracy; "always predict browse" passes at 84%.
3. Hot-loaded model assigns ~0 probability to call and build for every input.
4. Bandit context vector is fed a structurally-deficient forecast distribution; arm selection biases back to the rules baseline indefinitely.
5. Drift detector (`forecast_residual` in `daemon.rs`) will compute residuals against this degenerate forecast — false-negative on real activity drift, since the model's "predicted everything is browse" matches the corpus's "applied_arm is mostly browse" trivially.

## Root Cause
- **Trainer / rules-baseline coverage mismatch.** The trainer's 5-class taxonomy was sized to the full `Arm` set in `configs/sy/power.toml` (which includes `build`/`flat-out`/`npu-burst`), but the rules baseline that produces all onboarding-period labels covers only 5 of the 8 arms (and `meeting` rarely fires). The two were designed independently; nothing in the trainer's validation gate enforces that the corpus actually exercises every class.
- **No class-coverage invariant.** `MIN_TRAINING_ROWS` is a corpus-size gate; there's no `MIN_ROWS_PER_CLASS` gate.
- **No SPEC-level acknowledgement that the day-14 first-train will land on a rules-baseline-derived corpus.** The architecture assumes the trainer will see a balanced cross-section of arm picks, but the daemon spends 14 days NOT making bandit picks (per Step 26's onboarding gate).

## Fix
1. **Add a class-coverage gate to `retrain_gru`** (`src/power/trainer.rs:319-372`):
   - After `read_labelled_rows` produces `rows`, compute `class_counts: [usize; FORECAST_CLASS_COUNT]`.
   - If any class has `< MIN_ROWS_PER_CLASS` (suggest `MIN_ROWS_PER_CLASS = 16`), return new error variant `TrainerError::InsufficientClassCoverage { missing: Vec<String>, counts: [usize; 5] }`.
   - Errors surface to the daemon's `SpawnBlockingRetrainTrigger::dispatch` (`daemon.rs:146-171`) which already logs `trainer retrain failed`; extend the log line to include the missing classes for operator visibility.
2. **Add a per-class recall floor to `run_validation`** (`src/power/trainer.rs:848-873`):
   - Compute per-class recall over the held-out set.
   - Reject (`TrainerError::ValidationFailed("per-class recall floor: class X recall = Y < 0.5")`) if any observed class has recall < 0.5.
   - The argmax-accuracy check stays as a secondary signal.
3. **Surface gap on `sy power status`** (`src/power/status.rs` + IPC schema):
   - When the daemon refused to ship the last trained model due to class-coverage failure, `status.model` should include a `missing_classes: ["call", "build"]` field. `sy power status --json | jq .model` becomes the operator's affordance for noticing this.
4. **Tests** (`src/power/trainer.rs::tests`):
   - `rejects_when_class_has_zero_rows` — synthetic 200-row corpus with only browse/idle/code; assert `Err(InsufficientClassCoverage { missing: ["call", "build"], .. })`.
   - `rejects_when_per_class_recall_below_floor` — corpus with 50 browse + 5 code rows; trainer fits trivially-browse model; validation gate rejects on code recall = 0.
   - `accepts_when_all_classes_meet_floor` — balanced 200-row synthetic corpus; trainer succeeds.
5. **Roadmap follow-up (out of scope for this BUG):** the deeper question — "how does the daemon ever collect `call`/`build` labels during onboarding?" — has two paths worth filing as separate journey items:
   - Loosen the onboarding bandit gate to allow ε-greedy exploration (so the trainer corpus contains all arms by day 14).
   - Extend `rules_baseline` to map shield states to the missing arms (e.g. `cool_ac + npu_workloads_high` → `npu-burst`).
   Both are design decisions beyond the scope of "trainer must refuse to ship a degenerate model".
