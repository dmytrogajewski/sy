# BUG-20260712-1046: `ThrashTracker` permanently locks out all arm switches — `record` refreshes `last_change` on every 1 Hz tick

## Summary
`src/power/shield/project.rs` — `project()` calls
`thrash.record(&candidate.name, now)` on EVERY tick, including unchanged
re-picks of the same arm. `ThrashTracker::record()` refreshed
`last_change` unconditionally, so at the daemon's 1 Hz tick cadence
`last_change` was always ≤1 s old. The anti-thrash guard
`would_thrash(new != last, now - last_change < 30 s)` was then true for
ANY arm switch, so `project` took the `break` and fell back to the
rules baseline. The net effect: once the daemon reaches steady state on
an arm, no pin and no future bandit arm selection can ever change the
applied arm — the core value of the plane is silently defeated.

## Reproduction
- Method: live host probe (2026-07-12) plus source trace.
- Live evidence: `sy power profile flat-out` pinned the arm — the
  `reason_chain` showed `pin:flat-out` — but `applied_arm` stayed
  `browse` forever. The 1 Hz daemon loop re-recorded the steady-state
  arm each tick, refreshing `last_change` to `now` continuously; only
  shield-baseline-path switches (which the guard does not gate) ever
  changed the applied arm.
- Source trace: at 1 Hz, ticks 1..N re-pick the same arm; each
  `record(same_arm, now)` slid `last_change` to that tick. On the tick
  a switch was proposed, `now - last_change ≈ 1 s < 30 s` →
  `would_thrash` true → `break` → baseline.

## Expected
A pinned or bandit-proposed arm switch takes effect on the next tick
once `profile_thrash_min_interval_s` (default 30 s) has elapsed since
the last *actual* arm change — regardless of how many unchanged
re-picks happened in between.

## Actual
`last_change` marked the last `record` CALL, not the last arm CHANGE.
Because `project` records on every tick, the 30 s window never elapsed
relative to the previous tick, so every arm switch was blocked and the
daemon collapsed to baseline in perpetuity. `applied_arm` stuck at
`browse` despite `pin:flat-out` in the reason chain.

## Root Cause
`ThrashTracker::record()` wrote a fresh `last_change = now` on every
call, including same-arm re-picks. Combined with `project()`'s
record-on-every-tick, the anti-thrash floor's reference point was
continuously reset, so the `min_interval` guard never cleared.

## Severity / Impact
Critical. Silently defeats manual pins AND all future bandit arm
selection — the plane appears to run but never applies anything other
than the conservative baseline. No crash, no error, no log signal:
`reason_chain` truthfully shows the intended pick while `applied_arm`
diverges.

## Fix
`ThrashTracker::record()` now leaves `last_change` untouched when the
recorded arm equals the currently recorded arm; it only stamps a new
`last_change` on an actual arm change. `last_change` therefore marks
the last real transition, so the 30 s floor measures time since the
last change (not the last tick), and a switch goes through once the
floor has genuinely elapsed. The guard's real purpose is preserved: a
rapid A→B→A flap within the window still collapses to the baseline
because each of those *is* an attempted change inside the interval.

## Tests (`src/power/shield/project.rs`)
- `arm_switch_takes_effect_after_steady_repicks` — reproduces the
  lockout: after 60 unchanged re-picks at 1 Hz, a switch to `flat-out`
  must take effect (FAILED before the fix, returned `browse`).
- `repick_does_not_refresh_last_change` — an unchanged re-pick 29 s in
  must not slide the window; a switch 31 s after the real change is
  allowed (FAILED before the fix).
- `rapid_flap_within_window_still_suppressed` — regression guard: a
  genuine A→B→A flap inside the window still collapses to baseline.
- Existing `profile_thrash_limit_30s` and the rest of the module stay
  green.
