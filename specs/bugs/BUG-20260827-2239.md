# BUG-20260827-2239: Spark truncates valid Ornith agent turns at 4,096 tokens

## Summary

The Responses adapter invents a 4,096-token output limit when Codex does not
send one, and the llama.cpp declaration caps every model at 65,536 context
tokens. Ornith's valid long agent turns are therefore truncated even though
the model and engine remain healthy.

## Reproduction

- Method: real-device fresh Codex run plus declarative-policy unit tests
- Tests:
  `spark::engine::tests::llama_context_is_loaded_from_each_model_instead_of_globally_capped`,
  `spark::gateway::tests::responses_string_input_translates_to_native_vllm_chat`,
  `spark::gateway::tests::responses_forwards_an_explicit_output_limit_without_inventing_a_default`,
  and `spark::engine::tests::llama_profile_uses_precise_coding_sampling`
- Command: `sy spark dgx-spark launch codex --model ornith-1.5:9b-q4-k-m -- exec --skip-git-repo-check --ephemeral --sandbox workspace-write --json <PROMPT>`
- Evidence: two consecutive streamed responses generated exactly 4,096 reasoning
  tokens each without a completed file-write call; Codex reported
  `Incomplete response returned, reason: max_output_tokens`. The run was
  stopped after 225.46 seconds with no files created. Engine decode throughput
  remained 34.9-36.7 tokens/s, isolating behavior from compute performance.
  A separate real Spark request with reasoning enabled produced a correctly
  streamed `shell({"cmd":"echo READY"})` tool call in 51 completion tokens.
  This disproves the earlier hypothesis that reasoning itself must be disabled.

  Ollama 0.32.5's generated Codex catalog advertises the same local Ornith Q4
  model with a 262,144-token context, and its Responses adapter forwards an
  output limit only when the client supplies one. Ollama also selects its
  dedicated Ornith renderer and Qwen3.5 parser.

## Expected

The default GGUF path preserves the client's optional output-limit semantics,
loads the context length from each model's own GGUF metadata, keeps reasoning
enabled, and emits actionable tool calls without premature truncation.

## Actual

The gateway converted an absent `max_output_tokens` into `max_tokens=4096`.
The shared llama.cpp declaration also forced `--ctx-size 65536`, overriding
Ornith's 262,144-token model metadata.

## Root Cause

`response_max_tokens` treated an optional OpenAI Responses field as a required
field with a sy-local default. Independently, the engine declaration used a
fixed context size instead of llama.cpp's model-derived `--ctx-size 0` mode.
Neither behavior came from a model recipe or client request.

## Fix

Do not insert `max_tokens` upstream when `max_output_tokens` is absent; preserve
and validate an explicit client value. Configure llama.cpp with `--ctx-size 0`
so each GGUF's own context metadata is authoritative. Retain the publisher's
precise-coding sampling defaults and leave reasoning enabled.
