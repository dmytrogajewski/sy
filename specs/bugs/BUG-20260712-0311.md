# BUG-20260712-0311: shield reports `COOL_AC` while on battery — the DFA state vocabulary conflates thermal state with power source

## Summary
`sy power status` on this host reported `shield_state = COOL_AC` while the
AC sensor read `ac = false` (battery, ~90% SOC). The label is misleading:
`COOL_AC` literally names AC power, but the shield DFA emits it for the
DC (battery) case whenever the battery is *not* low. The 5-state
vocabulary (`COOL_AC | WARM_AC | HOT | BATTERY_LOW | MEETING`) only
distinguishes battery from AC once SOC crosses `battery_low_dc_pct`
(25%) / `battery_emergency_dc_pct` (10%). Between 25% and 100% on
battery the DFA falls through the DC branch and returns a thermal state
whose name asserts AC. This was surfaced while implementing sy-power S5
(one-JSON-document `status --json` + NPU probe caching); it is filed
rather than fixed because a correct fix expands the state vocabulary and
ripples across the rules baseline, projection, and config — out of scope
for S5.

## Reproduction
- Method: live `sy power status --json` on the audit host (2026-07-12),
  cross-referenced with `src/power/shield/dfa.rs::transition`.
- Live evidence:
  ```
  sensors.ac        = false        # on battery
  sensors.battery_pct ≈ 90
  shield_state      = "COOL_AC"    # name asserts AC power
  ```
- Code-level walk (`src/power/shield/dfa.rs::transition`, cool/healthy
  battery input):
  1. `call_active` false, `prev != Meeting` → not `MEETING`.
  2. `ac_online = false` → enter the DC branch, but `soc (90) >
     battery_low_dc_pct (25)` and `> battery_emergency_dc_pct (10)` →
     no `BATTERY_LOW`, fall through.
  3. `tctl_c` below `tctl_sustained_60s_avg_c (80)` → not `HOT` / `WARM_AC`.
  4. Return `ShieldState::CoolAc`.
- Thresholds: `src/power/config.rs` — `battery_low_dc_pct = 25`,
  `battery_emergency_dc_pct = 10`, `tctl_act_c = 85`,
  `tctl_sustained_60s_avg_c = 80`.

## Expected
The reported state should not claim AC power while the machine is on
battery. Either (a) a distinct DC thermal state (`COOL_DC` / `WARM_DC`),
or (b) the state name should be power-source-neutral (e.g. `COOL` /
`WARM`) with AC/DC carried as a separate axis, so an operator or agent
reading `shield_state` is not told "AC" while `sensors.ac == false`.

## Actual
`COOL_AC` (and, at higher temps, `WARM_AC`) is emitted for the healthy-battery
DC case. The `_AC` suffix is a fixed part of the enum variant, so the
DC/AC distinction is only visible via the separate `sensors.ac` field —
the two fields disagree at face value.

## Root Cause
The shield DFA's output vocabulary encodes power source into the thermal
state name, but only branches on power source at the low-battery
threshold. For SOC in `(battery_low_dc_pct, 100]` the DC path deliberately
falls through to the same thermal states used on AC, and those states are
named `*_AC`. This is a *labeling* defect driven by the enum design, not
a sensor-input error: `raw.ac_online` is read correctly (`false`), and
the DFA's low-battery guard works; the healthy-battery DC case simply has
no dedicated label and inherits the AC one.

## Severity / Impact
Low-to-moderate. Not a safety issue (thermal and emergency-battery
guards are unaffected). The concrete consequences:
1. Operator/agent confusion: `shield_state` and `sensors.ac` contradict
   each other in `sy.power.status/v1`.
2. Policy nuance: on healthy battery the daemon applies the
   `rules_baseline.cool_ac` / `warm_ac` arm — the AC-tuned baseline —
   rather than a DC-aware one. Whether that is desirable (Apple-style
   "don't throttle until battery is actually low") is a policy question,
   but today it is implicit in the label collision rather than an
   explicit choice.

## Suggested Fix (deferred — not done in S5)
Introduce DC thermal states or make the thermal axis power-neutral:
- Add `CoolDc` / `WarmDc` to `ShieldState` (`dfa.rs`), with `as_str` /
  `parse` round-trips and NDJSON forward-compat.
- Extend `rules_baseline` (`config.rs` + `configs/sy/power.toml`) with
  `cool_dc` / `warm_dc` arm keys (may alias the AC arms initially to
  preserve behaviour, making the relabel behaviour-preserving).
- Thread the new states through `shield::project` constraints and the
  `explain` / waybar renderers.
- Property test: for every `(soc, ac, tctl)` the emitted state's power
  suffix matches `raw.ac_online` (never `*_AC` while `ac_online == false`).

## Notes
Filed from sy-power S5. S5 itself did not touch the shield DFA; the
`_AC`-on-battery observation was noted during the same audit and is
