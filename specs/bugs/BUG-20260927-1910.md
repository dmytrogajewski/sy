# BUG-20260927-1910: correct answers were answered with silence

## Summary

Two independent defects made `sy knowledge search` return **nothing** for
questions the retriever had actually answered, and made `make eval` report the
failure as a *retrieval* problem:

1. **The confidence calibrator double-applied the sigmoid.** The rerank
   workload's ONNX export bakes `sigmoid(logits[..])` into the graph, so its
   scores are already probabilities in `[0,1]`
   (`src/aiplane/workloads/rerank.rs` module docs). `calibrate::confidence()`
   assumed raw logits and applied another sigmoid, squashing every
   confidence into `[0.25, 0.54]`. The documented `0.5` abstain cutoff landed
   *inside* the range of correct answers.
2. **The eval gate scored recall on abstained responses.** It passed
   `abstain_threshold: Some(0.5)` and then measured `recall@k` over the
   returned hits — and the daemon answers an abstained request with an *empty*
   hit list. Every suppressed query became a retrieval miss, so `recall@1`
   equalled `recall@5` for the entire suite, which reads as "the retriever
   either nails rank 1 or never finds the chunk".

A third, separate defect was in the golden set itself: its four `date-range`
answerable rows windowed **2025–2027**, a period with **zero indexed points**
— the windows had been derived from the Telegram export's file mtime
(2026-06-04), not from the per-message `date` payload, which runs 2020–2024.
Those rows were unsatisfiable by construction and pinned `recall@5` at 0.667.

## Reproduction

- Method: manual, against the live index (115 522 points, 6 141 of them
  search-visible after `DEFAULT_EXCLUDED_KINDS`).
- Command: `make eval`

  ```text
  { "recall_at_1": 0.400, "recall_at_5": 0.400, "mrr": 0.400,
    "abstain_accuracy": 0.583, "n": 24 }
  ```

- Evidence, same queries through the CLI with abstention disabled
  (`sy knowledge search … -k 5 --candidates 8`) — the gold chunk is at rank 1
  with a rerank score of 0.85–1.00 while the gated path returned nothing:

  ```text
  rank=1  s0=0.996  conf=0.533  answered    бойлер включается подогревает воду
  rank=1  s0=0.957  conf=0.465  SUPPRESSED  записываю смешной кружочек …
  rank=1  s0=0.965  conf=0.429  SUPPRESSED  приятного аппетита кушай …
  rank=1  s0=0.852  conf=0.480  SUPPRESSED  встреча потом еще встреча …
  rank=-   (0 candidates)        SUPPRESSED  холтер хороший аритмия …   <- date window 2026-06
  ```

  The arithmetic is visible in `conf`: a 0.996 probability becomes
  `sigmoid(0.996) * sigmoid(0.996-0.002) = 0.730 * 0.730 = 0.533`, and a
  0.957 with a nearer rival becomes `0.722 * 0.636 = 0.465` → below 0.5 →
  `results: []`.

## Expected

REQ-6: a caller who asks with `abstain_threshold: 0.5` gets either the ranked
answers or an honest abstain — never silence about a chunk the reranker
scored 0.96. REQ-9: the gate separates *retrieval* regressions from *policy*
regressions instead of conflating them.

## Actual

`knowledge_search` returned `{results: [], abstained: true, confidence: 0.47}`
for 5 of 15 answerable golden queries. `make eval` blamed the retriever.

### Correction to BUG-20260927-1610

BUG-20260927-1610 recorded a "structural finding" that chunk payloads carry
no per-message date and that `date_from`/`date_to` therefore cannot
discriminate inside Telegram. **That finding is wrong** and the work it
proposed (extract Telegram `date` into the payload, add a qdrant datetime
index, map `SearchFilter::date_*` onto it) is already implemented and works:

```console
$ curl -s localhost:6333/collections/sy_knowledge | jq .result.payload_schema.date
{ "data_type": "datetime", "points": 6141 }
```

A telegram chunk's payload carries `date`, `from`, `message_id`,
`reply_to_id`, `has_media`; `qdrant::build_filter` already compiles
`date_from/date_to` to `{key: "date", range: {gte, lte}}`, and a
2021-scoped count returns 482 points. The pipeline emits those fields from
`pipeline/telegram/json.rs`; the *voice* sidecar does too. What was missing
was a golden set that used them — which is what BUG-20260927-1610's own
`date-range` rows got wrong, by reading `file_mtime` instead.

## Root Cause

`confidence(scores)` is a pure function whose input contract was never
pinned. SPEC §2 describes bge's *raw* logit card values (−8.19 → 0.00028,
+5.26 → 0.9948) and REQ-6 asks for "sigmoid(reranker logit) + top1−top2
margin". The ONNX export already performs that sigmoid inside the graph, so
implementing the SPEC sentence literally applied the transform twice.
Monotone transforms preserve *ranking*, which is why nothing else broke and
why the eval — which never inspected `confidence`, only the emptiness it
caused — reported it as a recall problem.

## Fix

- `src/knowledge/calibrate.rs` — rewritten against the `[0,1]` contract:
  confidence **is** the top-1 probability (clamped), discounted by up to half
  when the top-2 rival is tied (`0.5 * (1 + tanh(2·margin))`, 0.5 at an exact
  tie, ≈0.96 for a decisive lead). The dead `sigmoid` helper is deleted; the
  contract and the superseded behaviour are documented in the module header.
  Eight unit tests, including the two that pin this bug:
  `decisive_top1_confidence_is_its_own_probability` and
  `confident_near_tie_is_not_suppressed`.
- `src/knowledge/cli.rs` — `run_query_live` requests the search with
  abstention **off** and derives the flag through the new pure
  `eval_ranked(ids, confidence)` seam, so recall is always measured on the
  ranking the policy would have shown.
- `src/knowledge/eval.rs` — new axis
  [`Metrics::false_abstain_rate`](../../src/knowledge/eval.rs): the share of
  answerable queries whose gold is in the top-5 but which the policy
  suppressed, gated as a **ceiling** (`Tolerance::max_false_abstain_rate`)
  rather than a floor. This is the metric that names the bug class; recall
  cannot express it. `RankedResult` gained `confidence`, and `eval --json`
  gained a `per_query` array (`{query, answerable, rank, confidence,
  abstained}`) so a regression names its query instead of only its metric —
  SPEC §4.7's keys stay at the JSON root, `per_query` is additive.
- `src/knowledge/eval.rs` — `relevant()` refuses to match an empty gold.
  Unanswerable rows carry `expected: ""` and `str::contains("")` is `true`
  for every string, so every unanswerable row looked like a rank-1 hit in the
  new diagnostic (and would inflate recall for any answerable row whose label
  went missing).
- `specs/knowledge-feedback-iter1/eval/queries.jsonl` — the four
  unsatisfiable `date-range` rows now window the gold's real message date
  (2022-07, 2022-10, 2023-04, 2024-02, recorded per row as `_gold_date`); the
  three date-scoped abstain negatives moved to periods with no indexed data
  (2025-03, 2025-09, 2026-02); `рецепт борща…` — which the corpus does
  contain, rerank 0.99 — was replaced by a proven-absent topic
  (`замена ремня грм…`, rerank 0.001). Two static tests keep the file honest:
  answerable rows carry a gold, windows are not inverted, and every
  `_gold_date` lies inside its own window.

## Residual

- Two answerable rows legitimately fail: `Кениг … дело до 10.07` (top-1
  probability 0.15 — the reranker is genuinely unsure) and `зарплатки …` (the
  gold is outside the top 5). Both are now visible as named rows rather than
  anonymous misses.
- `sy knowledge search --kind` could not name `telegram-voice`, although
  4 132 of the 6 141 search-visible points carry that kind (a per-record
  override from `pipeline::telegram::VOICE_KIND`, not a `SourceKind` clap
  variant), so two thirds of the voice corpus was unfilterable from the CLI
  while the daemon-side filter had always matched on it. Fixed in the same
  pass: `sources::SearchKind` is the search-facing enum (every `SourceKind`
  plus `TelegramVoice`, kebab strings delegated to `SourceKind::as_kebab` so
  they cannot diverge on the wire), and `search_kind_covers_every_source_kind`
  fails if a future `SourceKind` variant is left unselectable.
  `--kind telegram-voice` now returns voice notes and only voice notes.
- `aiplane.batch` still bypasses the scheduler (BUG-20260927-1830).
- `agent-history` remains 94.7 % of the collection while being excluded from
  default search: 109 381 embedded points that cost NPU hours to build and can
  never be recalled by default. Indexing policy for it is an open decision.
