# BUG-20260927-1215: chunker budgeted whitespace tokens against a wordpiece window, silently indexing unsearchable content

## Summary

`chunk_sized` cut documents into windows of N *whitespace tokens* (640 for the
generic pipeline) and nothing bounded the result in characters.
`aiplane::workloads::embed::encode` runs a static `(1, 512)` graph and does
`ids.truncate(512)`, so every character past 512 *wordpieces* is written to
qdrant, never embedded, and unreachable by search — a chunk that indexes
green and searches as if it were empty. For whitespace-poor payloads the
token budget stops being a bound at all: this corpus contains a single chunk
of **1 039 923 characters** (max sampled now: 240 524).

## Reproduction

```bash
python3 - <<'PY'   # longest chunks actually in the index
import json,urllib.request as u
best=0
off=None
for _ in range(120):
    b={"limit":256,"with_payload":["chunk_text","kind"]}
    if off: b["offset"]=off
    r=json.load(u.urlopen(u.Request("http://127.0.0.1:6333/collections/sy_knowledge/points/scroll",
        data=json.dumps(b).encode(),headers={"Content-Type":"application/json"})))['result']
    for p in r['points']: best=max(best,len((p.get('payload') or {}).get('chunk_text') or ''))
    off=r.get('next_page_offset')
    if not off: break
print(best)
PY
```

A 40 000-char whitespace-free blob came back as **one** chunk.

## Expected / Actual

| | expected | actual |
|---|---|---|
| one chunk's length | ≤ the embedder's window | 240 k chars, unbounded |
| content past 512 wordpieces | not indexed | indexed, never embedded, invisible |
| 40 k blob | ~23 chunks | 1 chunk |

## Root Cause

A unit mismatch, not a typo: the chunker counted **whitespace tokens**, the
model consumes **sentencepiece wordpieces**, and `GENERIC_CHUNK_TOKENS = 640`
was chosen inside a SPEC band of "500–800 tokens" that conflated the two.
Ordinary prose is ~1.3 wordpieces per whitespace token, so a 640-token window
was already ~700 wordpieces — `truncate(512)` dropped ~30 % of every generic
chunk. For minified JSON, base64, or `.jsonl`, one "token" is one line, so the
window became the file: the 1 M chunk measured 640 whitespace tokens averaging
**1 624 characters each**.

## Fix

`src/knowledge/chunk.rs` now budgets both ways: `MAX_CHUNK_CHARS = 1_800`
(~512 wordpieces at XLM-R's ~3.5 chars/wordpiece, in `char`s so Cyrillic gets
the same guarantee as ASCII) alongside the per-pipeline token target, and
`split_oversized` cuts a single oversized token on char boundaries so the cap
is absolute. Overlap stays at 64 tokens, indices stay dense from 0 (point ids
derive from `chunk_index`), and short documents are byte-identical to before.
Six tests in `chunk::tests` pin each property, including "the window must not
close far *below* the cap either".

## Verification

- `cargo test --bin sy knowledge::chunk` → 6/6; full suite 1500 passed, 0 failed;
  `make lint` and `cargo fmt --check` clean.
- Which budget binds is now explicit and tested: 1-char words → the token
  target (640) binds; 5-char words → the char cap (~280 words) binds.

## Findings from chasing this (all measured, so nobody re-runs them)

1. **The embedder is fine.** Exported ONNX vs the cached `intfloat/multilingual-e5-base`
   reference agree to 4 decimals (cosine 1.0000 on the same inputs); NPU and CPU
   EP outputs match; `query:`/`passage:` prefixes are applied correctly; mean-pool
   is masked properly and the graph emits exact unit norms.
2. **The model has a high cosine floor.** Same-text 0.91, unrelated 0.77, two
   unrelated *long* texts 0.86. So an indexed corpus of long mean-pooled windows
   collapses into a ~0.82 band and ranking looks like noise. That is a property
   of mean-pooled e5, not a sy bug — mitigations would be shorter chunks
   (now enforced), centering/whitening, or relying on the sparse + rerank legs.
3. **Both hybrid legs are populated** (200/200 sampled points carry a non-empty
   sparse vector); a gold-containing chunk did rank #2 for a representative
   query.
4. **`sy knowledge eval` is not currently a usable gate.** Baseline recall@1
   0.056 against a 0.300 gate: the golden set asks about X5/Магнит/Ozon/Лента
   promos, but the corpus is 25 MB of personal chat containing "Магнит" **6
   times** — most rows are labelled `answerable: true` with no gold present, so
   the metric measures the corpus, not the retriever. It needs re-authoring
   against content that exists.
5. **Re-index economics — why this fix ships without one:**

   | bucket | share of chunks over the 1.8 k cap | p50 length |
   |---|---|---|
   | whole corpus | 94.9 % | 4 999 |
   | search-visible (excluding `agent-history`) | **1.3 %** | **211** |
   | `agent-history` only | 99.6 % | 5 057 |

   The defect lives almost entirely in `agent-history`, which search excludes
   by default. A full `sy knowledge sync` costs hours of single-context NPU time
   (the graph is static batch-1) to fix 1.3 % of what default search can reach.
   New content is chunked correctly from install time onward; the existing
   points converge at the next natural full resync (schema bump or model
   change), or on demand for a named subset.

## Follow-ups (not in this fix)

- Re-author `specs/knowledge-feedback-iter1/eval/queries.jsonl` against the real
  corpus (or gate `make eval` on the subset that is genuinely answerable).
- If `agent-history` should be searchable at all, re-index that subset alone.
- Consider corpus-mean centering for the dense leg, and a chunk-schema version so
  a chunker change can invalidate the index deliberately.
