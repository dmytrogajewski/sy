# BUG-20260712-1530: `sy power status` onboarding block lies when CLI and daemon disagree on `SY_POWER_ONBOARDING_DAYS`

## Summary
`sy power status` (and the MCP `power_status` tool via
`build_live_status_value`) computed the `onboarding` JSON block
CLI-side, using `cfg.onboarding.days` as loaded in the **CLI process**.
The `sy-powerd` daemon loads its own config + env and enforces the gate
independently. When the two disagree — the concrete repro on this host: a
systemd drop-in sets `Environment=SY_POWER_ONBOARDING_DAYS=0` for
`sy-powerd` only — the status document reports
`onboarding.active=true, target_days=14` while the daemon's gate is
actually open (bandit live, trainer eligible). The status document lied
about the daemon's operational state.

## Reproduction
- Method: live daemon (systemd drop-in) + hermetic unit tests
- Tests:
  - `crate::power::daemon::tests::status_response_carries_daemon_onboarding_block`
  - `crate::power::status::tests::onboarding_block_prefers_daemon_reported_view`
  - `crate::power::status::tests::onboarding_block_falls_back_when_daemon_field_absent`
- Command (live, 2026-07-12), with the drop-in active:
  ```
  sy power status --json | jq .onboarding
  # → {"active": true, "days_collected": 5, "target_days": 14}

  SY_POWER_ONBOARDING_DAYS=0 sy power status --json | jq .onboarding
  # → {"active": false, "target_days": 0}
  ```
  Same daemon, two different answers — both computed client-side. The
  daemon's real gate (target_days=0) was open the whole time.

## Expected
The `onboarding` block on `sy power status --json` reflects the gate the
daemon is **actually** enforcing — the daemon is the source of truth for
its own onboarding window. The block is invariant to whatever
`SY_POWER_ONBOARDING_DAYS` the querying process happens to load.

## Actual
`cli::status` and `cli::build_live_status_value` called
`onboarding::compute_onboarding_status(..., cfg.onboarding.days, ...)`
with `cfg` loaded in the CLI process, and `status::build_status_value`
stamped `target_days` from `cfg.onboarding.days`. Neither consulted the
daemon. The waybar path (`format_waybar` → `waybar_text`) had the same
CLI-side dependency for its "learning Xd Yh" countdown and `onboarding`
class.

## Root Cause
The onboarding gate was recomputed independently on each side of the IPC
boundary from each process's own config + env. The daemon's IPC `Status`
response (`StatusResponse`) carried the snapshot, last-audit, drift, and
model blocks but **not** its onboarding view, so the CLI had no
authoritative value to render and fell back to re-deriving it — a
derivation that diverges the moment the two processes load a different
`SY_POWER_ONBOARDING_DAYS`.

## Fix
Make the daemon serve its own onboarding view over the IPC it already
answers, and have the CLI prefer it:
- `src/power/ipc.rs`: add `OnboardingWire { active, days_collected,
  ready_at, target_days }` and an `Option<OnboardingWire>` field
  `StatusResponse::onboarding`, `#[serde(default,
  skip_serializing_if = "Option::is_none")]` so old ↔ new wire frames
  stay compatible in both directions. `target_days` carries the
  daemon's **effective** `cfg.onboarding.days` (post env-override).
- `src/power/daemon.rs`: new shared `LatestOnboarding` slot published by
  the tick loop right after it recomputes `OnboardingTickState::status`;
  the IPC `Status` handler copies it into `resp.onboarding`. The
  connection handler's shared slots were bundled into a `ConnState`
  struct to keep the fn under the clippy argument ceiling.
- `src/power/status.rs`: `effective_onboarding` resolves the render view
  — the daemon-reported block when present, else the CLI-side
  computation. `build_status_value` and `format_waybar` both route
  through it; the printed `onboarding` block keeps the same keys
  (`active`, `days_collected`, `ready_at`, `target_days`), so agents
  parsing it don't break. When the field is absent (pre-fix daemon), the
  fallback preserves the old behaviour exactly.
