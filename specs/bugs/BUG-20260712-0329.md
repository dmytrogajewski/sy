# BUG-20260712-0329: power daemon degrades loudly-then-silently — telemetry stops at the daily size cap, and a persistently failing actuator WARNs every tick forever

## Summary
Two failure modes in `sy-powerd` share the same anti-pattern: a degradation that starts as a per-tick journal storm and ends as silent data loss.

- **Problem A — daily size-cap starvation.** `Logger::append` (`src/power/log.rs`) enforced a per-day cap by writing a single `rotated:size_cap` marker and then **refusing every subsequent append for the rest of the UTC day** (`Err(LogError::SizeCap)`). The 1 Hz daemon calls `append` every tick, so a capped day produced ~86k `WARN tick append failed: audit log size cap reached for today` lines while collecting **zero** further telemetry. On the audit host `telemetry-2026-07-07.ndjson` sat exactly at the cap: the rest of that day never made it into the NDJSON, starving the offline trainer corpus and skewing any consumer that counts telemetry days.
- **Problem B — actuator-failure log storm.** A persistently failing actuator (the iGPU `pp_power_profile_mode` lever on this host) is retried on every tick and, via `daemon::log_apply`, emits a fresh `WARN actuator failed lever=…` line every second, indefinitely. There was no notion of "we already told you"; the journal fills with identical lines and the real signal (the *transition* into and out of the failed state) is buried.

Both are "degrade loudly, then silently" bugs: A goes silent (no data) after being loud; B stays loud forever. The fix makes both degrade *once*, then keep working.

## Reproduction
- Method: code audit + live daemon/journal state on the audit host (test-based repro lands with the fix per `/implement`).
- Problem A evidence:
  ```
  $ ls -l ~/.local/state/sy/power/telemetry-2026-07-07.ndjson
  -rw------- ... 41943040 ... telemetry-2026-07-07.ndjson   # exactly at the (then 40 MiB) cap
  $ journalctl --user -u sy-powerd -g 'size cap reached' --output=cat | wc -l
  # thousands of identical lines for that day; none after midnight boundary
  ```
  After the marker was written, `append` returned `SizeCap` on every tick, so no entry for the remaining hours of 2026-07-07 exists.
- Problem B evidence:
  ```
  $ journalctl --user -u sy-powerd -p warning -g 'actuator failed lever=igpu' --output=cat | wc -l
  # one line per tick since the lever started failing — grows without bound
  ```
- Code-level:
  - `src/power/log.rs::Logger::append` — `if current_size + line > max { write_size_cap_marker; return Err(SizeCap) }`. No rollover; the day is finished.
  - `src/power/daemon.rs::run_async` — logs `WARN "tick append failed"` on every `append` error, once per second.
  - `src/power/daemon.rs::log_apply` / the NPU branch in `apply_arm` — `WARN` on every failing tick with no latch/backoff.

## Expected
1. When the active telemetry file reaches the size cap, collection **continues** by rolling over to an overflow segment; no telemetry is dropped for the rest of the day.
2. The size-cap event is logged (WARN) **once per UTC day**, not once per tick.
3. Total disk stays bounded: the retention sweep deletes overflow segments on the same 7-day schedule as base files.
4. A persistently failing actuator lever WARNs **once** on entering the failed state, retries on a capped exponential backoff, and logs **once** on recovery.
5. The audit `reason_chain` still records the lever state every tick (cheap) — only the journal spam is suppressed, not the audit trail.

## Actual
1. At the cap, `append` returned `SizeCap` and stopped writing until midnight; telemetry for the rest of the day was lost.
2. The daemon logged the cap on every tick (~86k lines/day).
3. Retention only parsed `telemetry-YYYY-MM-DD.ndjson`; overflow files did not exist because rollover did not exist.
4. Every failing tick re-attempted the write and logged a fresh WARN forever.
5. (The reason chain already recorded lever state; that part was fine.)

## Root Cause
- **A: the cap was a stop-writing boundary, not a rotation boundary.** A daily hard cap with no overflow means "hit the ceiling ⇒ go dark". The correct primitive is segment rotation (like logrotate): fill a segment, mark it, roll to the next, and bound total disk via retention — not by refusing writes.
- **B: no per-lever failure state.** `log_apply` was stateless, so it could not distinguish "the lever just failed" (worth a WARN) from "the lever has been failing for an hour" (not worth another WARN). Without a latch + backoff the daemon cannot be quiet about a known-bad lever while still retrying it.

## Fix
Landed via `/implement`.

**Problem A — `src/power/log.rs`:**
1. `append` no longer refuses at the cap. It resolves the day's *active segment* via `active_segment_path`: the base file `telemetry-YYYY-MM-DD.ndjson` is segment 0; when a segment would exceed `max_size_bytes` the writer records the cap event once and rolls to `telemetry-YYYY-MM-DD.1.ndjson`, `.2`, … A zero-length segment always accepts the line (a single entry is never split; guarantees termination even if one entry exceeds the whole cap).
2. `record_size_cap` (renamed from `write_size_cap_marker`) writes the single `rotated:size_cap` marker into the full segment **and** emits one WARN, both deduped to once per UTC day via `LoggerState::capped_day` (plus the existing cross-restart file-tail dedupe from BUG-20260522-0037). So a day that rolls through many overflow segments logs the cap exactly once.
3. `parse_day_segment_from_path` parses `(day, segment)` from base and overflow filenames; `parse_day_from_path` delegates to it, so `rotate_retention` sweeps overflow segments on the same 7-day schedule (total disk stays bounded).
4. `collect_day_paths` returns `(day, segment, path)` and `tail` / `tail_count` sort by `(day, segment)` descending, so same-day overflow files order newest-first.
5. The `LogError::SizeCap` variant was retired (no longer constructed).

**Problem B — `src/power/apply/mod.rs` + `src/power/daemon.rs`:**
1. New `LeverLatch` (+ `ActuatorLatches` map, `LatchOutcome` enum) in `apply/mod.rs`: a per-lever state machine driven by the injected `Clock`'s `DateTime<Utc>`. It logs once on the failure edge, `Skip`s the sysfs write while inside a capped exponential backoff (`LATCH_INITIAL_BACKOFF = 1s` … `LATCH_MAX_BACKOFF = 60s`), and surfaces a single recovery edge when the write succeeds again.
2. `daemon::apply_arm` now drives all five levers (platform_profile, epp, igpu, npu, cgroup) through `apply_lever`, which maps each `LatchOutcome` to at most one journal line and exactly one reason-chain token. `log_apply` was replaced by `apply_lever` + `warn_actuator_failed` (preserves the BUG-20260525-2350 structured EPP `failed_policies`/`failed_paths` fields, and the NPU best-effort one-liner) + `failure_token` (NPU keeps its bounded `short_npu_reason` form).
3. `ActuatorLatches` is owned by `run_async` across ticks and threaded through `one_tick`.

## Tests (hermetic — TempDir + injected `MockClock`)
- `log.rs::size_cap_rolls_to_overflow_and_warns_once` (`#[traced_test]`): the cap append rolls to `telemetry-….1.ndjson`, returns `Ok`, keeps the pre-cap entry, and the cap WARN fires exactly once across multiple rolls.
- `log.rs::retention_sweeps_overflow_segments`: an 8-day-old base + overflow are swept; in-window base + overflow are kept.
- `log.rs::size_cap_marker_dedupes_across_logger_restarts`: updated to the rollover contract (appends keep succeeding; exactly one marker survives a restart).
- `apply/mod.rs::lever_latch_logs_once_backs_off_and_recovers`: Failed → Skipped (no I/O) → StillFailed → Recovered → Ok edges, with backoff doubling.
- `apply/mod.rs::lever_latch_backoff_caps_at_max`: backoff saturates at 60 s.
- `daemon.rs::log_apply_surfaces_no_policy_writable_failed_paths`: retargeted onto `apply_lever`; still asserts the structured EPP WARN + single reason token.

## Migration
No schema bump. Existing `telemetry-YYYY-MM-DD.ndjson` files are segment 0 and keep working unchanged; overflow segments only appear once a day actually caps. The production `DEFAULT_MAX_SIZE_BYTES` (200 MiB) means a normal 1 Hz day never caps at all — the rollover path is the safety valve, not the common case. On restart the latch state resets to healthy; a still-failing lever re-emits its single entry WARN once, then goes quiet again.
