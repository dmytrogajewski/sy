# BUG-20260927-2355: silence was indexed as content and outranked real messages

## Summary

150 of the 4 132 indexed `telegram-voice` chunks are not speech. Whisper
answers a silent video with an empty string, with one of its own sound-effect
labels (`[Music]`, `[heartbeat]`, `(footsteps)`), or by hallucinating a
syllable out of noise (`-`, `(`, `в`, one U+FFFD). Every one of those became a
qdrant point, and a one-character document embeds into a degenerate vector
that dense retrieval ranks *above* real messages.

This is not a rounding error in a far corner: voice transcripts are 4 132 of
the 6 141 search-visible points (67 % of what a default query can even see),
so the junk sat in the highest-volume part of the searchable corpus.

## Reproduction

```console
$ sy knowledge search "knowledge applet missing not working" --limit 3 --json
[ { "chunk_text": "-", "file_path": "…/round_video_messages/video (236).mp4", … },
  { "chunk_text": "(", "file_path": "…/round_video_messages/video (870).mp4", … }, … ]
```

Two round-video transcripts with no speech topped a query about the knowledge
applet. Same finding from the other side, on disk:

```console
$ find ~/knowledge/telegram -name '*.txt' -type f -size -12c | wc -l
153                                    # of 4 133 transcript sidecars
```

The junk shapes, counted across those sidecars: 50 empty, 13 U+FFFD, 25
sound-effect labels, the rest one or two stray characters. Under the shipped
rule 150 of them score below 4, and those are exactly the points
`sy knowledge prune` removed.

## Expected

Media with nothing sayable in it contributes nothing to the index.

## Actual

Every transcribed media file produced exactly one point, whatever the
transcript contained. Nothing between a silent video and a vector.

## Root Cause

`TelegramPipeline::voice_records` mapped each media reference to a `Record`
unconditionally, and `transcribe::transcribe_cached` persists whatever the
worker returned. The text path has always had a floor of sorts, because short
messages are coalesced into conversation windows rather than indexed one by
one; the transcription route arrived later (REQ-5) as a separate producer and
never got an equivalent judgement.

## Fix

- **`transcribe::has_speech` / `MIN_SPEECH_CHARS = 4`.** Signal is counted
  outside whisper's bracketed annotations, so `[Music]` scores zero, and only
  alphanumeric characters count, which discards the U+FFFD a failed decode
  leaves behind. The floor sits below every real word on purpose: measured on
  the 4 133 sidecars under the shipped rule, 129 carry zero signal and 23 more
  carry 1–3, against a median of 84, so the corpus walk rejects 150 (3.6 %) and no real
  words — a floor at 8 or 12 would start deleting content.
- **Script-weighted, because a flat character count is a script-biased
  censor.** An ideograph or kana is a whole morpheme, so `你好吗` ("how are
  you?") is a searchable phrase at three characters where `спасибо` needs
  seven. Counting them alike would have deleted Chinese, Japanese and Korean
  speech while keeping Russian. The test suite caught this, not a review.
- **Braces are not annotations.** The first corpus scan flagged 382
  `agent-history` points as silence — they were Rust (`{ kind:
  CheckpointRegionKind::DraftBound`). Whisper annotates with `[]` and `()`.
  Treating `{}` likewise would have deleted real code the moment anything
  reused this gate.
- **The gate is in the transcription route, not in the chunker.** Voice records
  bypass `chunk::chunk_sized` entirely (`text` is the transcript, chunk index
  0), so a chunker floor would not have caught this; and a *universal* floor
  driven by a transcript rule is what nearly ate the 382 code chunks.
  `TRANSCRIBED_KINDS` names the kinds the rule owns — today `telegram-voice`
  alone.
- **`sy knowledge prune [--apply]`.** A re-index cannot heal the existing
  points: the export JSON that yielded them is unchanged, so the pass skips the
  file by content hash and never revisits the media. Prune walks the
  transcribed kinds, re-applies the same predicate, and reports; deletion needs
  `--apply`. Dry-run by default, `--json` for agents.
- **Rejected transcripts stay cached.** The sidecar is still written, so a
  silent file is not re-transcribed on every pass — the work is wasted once,
  not every 30 minutes.

## Residual

- The 0-byte and junk sidecars stay on disk deliberately. They are a cache of
  "this media has no speech", which is exactly what stops whisper re-running
  on them each pass.
- 123 `agent-history` chunks also carry < 4 signal characters (punctuation-only
  lines from JSONL splitting). Left alone: that kind is excluded from the
  default search scope, and it is not a transcript, so this gate does not own
  it. Deleting it is a separate, policy-level decision.
- No universal chunker floor was added. This bug is a producer that never
  judged its own output; the fix is that judgement, not a global filter that
  guesses per-source whether three characters meant something.
- A degenerate short *real* chunk (a 4-character note) can still top a query.
  The durable answer is length-aware scoring or a min-document-length prior in
  calibration, not more deletion.
