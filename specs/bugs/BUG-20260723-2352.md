# BUG-20260723-2352: live retrain rejected by recall floor — saturated GRU + shield-poisoned labels

## Summary
With the BUG-20260723-2210 coverage deadlock fixed, the live retrain
still never ships: the trained model collapses on minority classes and
the per-class recall floor (correctly) rejects it. Two independent
defects compound: (1) the trainer consumes RAW sensor features whose
scales differ by four orders of magnitude, saturating every GRU gate;
(2) rows whose arm was clamped by a condition-reactive shield are
labelled with the clamped arm, poisoning classes with contradictory
feature vectors.

## Reproduction
- Method: test + live
- Tests: `power::trainer::tests::trains_on_raw_scale_live_features`
  (facet 1), `power::trainer::tests::drops_rows_clamped_by_reactive_shields`
  (facet 2)
- Evidence (facet 1):
  ```
  raw-scale separable corpus must train and clear the recall floor:
  ValidationFailed("per-class recall floor: class code recall = 0.000 < 0.5")
  ```
- Evidence (facet 2): `rows_used` = 260 (shield-clamped rows trained)
  vs expected 200.
- Live sighting (2026-07-23): `sy power train --in ~/.local/state/sy/power`
  → `validation failed: per-class recall floor: class idle recall = 0.000`.
  Corpus forensics: feature ranges f[0] 39–93 (°C), f[1] 3–54 (W),
  f[9] 0.01–31,944 (user_idle_s) — unnormalized; every `idle`-arm row
  sat >70 °C under `shield:HOT` (5,617 rows), every `whisper`-arm row
  under `shield:BATTERY_LOW` (1,489 rows).

## Expected
The trainer standardises features before SGD, ships the normalisation
inside the model, and never treats a shield-clamped arm as activity
evidence.

## Actual
`retrain_with_sink` fed raw features to Glorot-initialised weights
(pre-activations in the thousands → sigmoid/tanh saturate → gradients
vanish → majority-class collapse), and `read_labelled_rows_from_file`
kept HOT/BATTERY_LOW rows whose applied arm records the shield's
reaction (cool a hot machine, save a draining battery), not what the
user was doing.

## Root Cause
Facet 1: the synthetic fixtures all use 0–1 features, so the missing
normalisation was invisible to the suite; the daemon logs raw sensor
values per the snapshot schema. Facet 2: the five-class taxonomy
assumes `applied_arm ≈ user activity`, which holds for pins, bandit
picks, and activity-driven baseline choices — but not when the shield
DFA overrides the arm on thermal/battery conditions.

## Fix
Facet 1: `FeatureStats` (per-feature mean + inverse std, zero-variance
columns zeroed) computed over the covered corpus; SGD trains on
standardised windows; `export_onnx` prepends `Sub(mean)` / `Mul(1/std)`
nodes so the on-disk model still consumes RAW daemon features — no
daemon-side changes, validation exercises the same contract. Facet 2:
`ACTIVITY_CLAMPING_SHIELDS = [HOT, BATTERY_LOW]` rows are dropped in
the corpus reader (`MEETING` is kept — it fires off the call-active
sensor and is genuine `call` evidence).

## Remaining blocker (design-level, out of bug scope)
With both facets fixed, the live retrain still fails
(`browse recall = 0.000`): under the rules baseline the default arm
(`browse`) is applied across every real activity regime (97% of
nominal rows), so the labels carry almost no activity signal — e.g.
the validation tail (2026-07-23) is hours of heavy compilation
labelled "browse". No trainer change can conjure signal the labels
don't contain. Shipping a model requires a label-source decision
(e.g. supervise from the sensor-derived activity classifier instead of
`applied_arm`, or accrue pin/bandit-labelled rows) — SPEC-level,
needs /research + /journey.
