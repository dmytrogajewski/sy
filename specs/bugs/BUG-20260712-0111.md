# BUG-20260712-0111: iGPU actuator fails ~1 Hz — udev rule matches `ATTR{vendor}` on the drm node, but `vendor` lives on the PARENT PCI device (needs `ATTRS{vendor}`)

## Summary
`configs/udev/rules.d/99-sy-power.rules` grants `sy-powerd` write access to
the AMD iGPU's `power_dpm_force_performance_level` knob by matching the PCI
vendor ID. It uses the same-device operator `ATTR{vendor}=="0x1002"` on a
`SUBSYSTEM=="drm"` event. But `vendor` is a PCI attribute exposed on the drm
node's **parent** device (`/sys/class/drm/cardN/device/vendor`), not on the
drm class node itself (`/sys/class/drm/cardN/` has no `vendor` attribute).
`ATTR{...}` only reads attributes on the event device, so the match is
*always* false, the rule never fires, and
`power_dpm_force_performance_level` stays `0644 root:root` after every boot.
The user-level `sy-powerd` (in `wheel`) cannot write it, so the iGPU
actuator fails ~1 Hz: **2989** `WARN actuator failed lever=igpu` lines
across 07-08..07-11. This is the sole live actuator failure on the host.
The fix is one operator: `ATTR{vendor}` → `ATTRS{vendor}` (parent-walking).

## Reproduction
- Method: sysfs + udevadm + journal probe on the live host (regression test
  lands with the fix per `/implement`).
- iGPU is `card1` (AMD `0x1002`); `card0` is the NVIDIA dGPU (`0x10de`).
  The kernel renumbers these across boots, which is why the rule keys on
  vendor rather than a fixed card index.
- `vendor` is on the PARENT PCI device, not the drm class node:
  ```
  $ cat /sys/class/drm/card1/device/vendor
  0x1002                                  # parent PCI dev — present
  $ ls /sys/class/drm/card1/vendor
  ls: cannot access '/sys/class/drm/card1/vendor': No such file or directory
                                          # drm class node — NO vendor attr
  ```
- The knob is unwritable by `sy-powerd` — rule never applied its chmod/chgrp:
  ```
  $ ls -l /sys/class/drm/card1/device/power_dpm_force_performance_level
  -rw-r--r--. 1 root root ... power_dpm_force_performance_level
                                          # 0644 root:root, want 0664 root:wheel
  ```
- `udevadm test` (non-sudo, debug-only — does NOT execute RUN keys) reads the
  rule file but never reaches our `power_dpm` RUN action, because the
  `ATTR{vendor}` match short-circuits:
  ```
  $ udevadm test /sys/class/drm/card1 2>&1 | grep -i 'sy-power\|power_dpm'
  Reading rules file: /etc/udev/rules.d/99-sy-power.rules
  # (no line adding the power_dpm_force_performance_level chmod/chgrp RUN)
  ```
- Journal evidence (JSON logs — grep the `"lever":"igpu"` field, not a
  space-separated string):
  ```
  $ journalctl --user -u sy-powerd.service --since '2026-07-08' \
      | grep -ic 'actuator failed'
  2989
  $ journalctl --user -u sy-powerd.service --since '2026-07-08' \
      | grep -i 'actuator failed' | head -1
  ... "message":"actuator failed","lever":"igpu",
      "error":"write /sys/class/drm/card1/device/power_dpm_force_performance_level" ...
  ```
  (~1 line/second whenever the daemon reconsiders the iGPU lever.)

## Expected
1. `99-sy-power.rules` matches the AMD iGPU by walking to the parent PCI
   device: `ATTRS{vendor}=="0x1002"`.
2. On drm `add`/`change`, udev chmods `power_dpm_force_performance_level` to
   `0664` and chgrps it to `wheel`, so `sy-powerd` can write it regardless of
   which `cardN` index the kernel assigned this boot.
3. No `actuator failed lever=igpu` lines in the daemon journal under
   steady-state operation.

## Actual
1. The rule matches `ATTR{vendor}=="0x1002"` (same-device). The drm class node
   exposes no `vendor` attribute, so the condition never holds.
2. The `RUN+=` chmod/chgrp never executes; the knob stays `0644 root:root`.
3. Every iGPU-lever reconsideration in `sy-powerd` fails its write and logs
   `WARN actuator failed lever=igpu` (2989 lines over 07-08..07-11).

## Root Cause
- **udev operator confusion.** `ATTR{key}` matches an attribute on the event
  device only; `ATTRS{key}` walks the parent chain. PCI `vendor`/`device`
  attributes live on the PCI device, which is the *parent* of the drm class
  node the `SUBSYSTEM=="drm"` rule triggers on. Keying on `ATTR{vendor}` for a
  parent attribute is a match that can never be true, so the rule is inert.
  The header comment on the rule made the same mistake, documenting
  `ATTR{vendor}=="0x1002"`.

## Fix
1. `configs/udev/rules.d/99-sy-power.rules`: change the vendor match from
   `ATTR{vendor}=="0x1002"` to `ATTRS{vendor}=="0x1002"` (and correct the
   header comment to match). This is the whole code fix — the `RUN+=` chmod/
   chgrp action and the `KERNEL=="card*"` / `SUBSYSTEM=="drm"` scoping are
   already correct.
2. Regression test `tests/udev_rules.rs::drm_vendor_match_uses_parent_walking_attrs`
   (new file, mirrors `tests/tmpfiles_policy_coverage.rs`): asserts the shipped
   rules file matches the AMD vendor via parent-walking `ATTRS{vendor}` and
   never via same-device `ATTR{vendor}`. Pins the regression so a future edit
   can't silently reintroduce the inert form.

## Verification
- Non-sudo (what this environment can prove):
  - `tests/udev_rules.rs` green.
  - `udevadm test /sys/class/drm/card1` reads the rule without error (debug
    mode does not run RUN keys, so it cannot flip perms — expected limit).
  - Confirmed structurally that `vendor` exists only at
    `card1/device/vendor` (parent) and not at `card1/vendor` (drm node),
    which is exactly why `ATTRS` is required.
- Operator deploy step (requires root — NOT performed here):
  ```
  sudo install -m 0644 configs/udev/rules.d/99-sy-power.rules \
      /etc/udev/rules.d/99-sy-power.rules
  sudo udevadm control --reload-rules
  sudo udevadm trigger --subsystem-match=drm
  # verify:
  ls -l /sys/class/drm/card1/device/power_dpm_force_performance_level
  #   -rw-rw-r--. 1 root wheel ...   (0664 root:wheel)
  journalctl --user -u sy-powerd.service -f | grep 'lever=igpu'
  #   no more 'actuator failed'
  ```
  Until the operator reloads udev and re-triggers, the live knob stays
  `0644 root:root` and the WARNs continue — the repo fix alone cannot flip
  host permissions without sudo.
