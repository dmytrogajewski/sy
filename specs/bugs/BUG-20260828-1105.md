# BUG-20260828-1105: Flash-Next agent request trips the memory guard

## Summary

The patched-vLLM engine starts and passes protocol probes, but its first large
Claude request causes sustained full-memory pressure and the Spark executor
correctly stops the container.

## Reproduction

- Start generation 5 with `gpu-memory-utilization=0.85`.
- vLLM reserves 17.08 GiB for 617,593 KV-cache tokens.
- Send a fresh Claude Code Tetris request through the Anthropic route.
- The executor records three pressure samples and stops the engine at 12.09%
  full-memory PSI with 8,693,096,448 bytes available.

## Expected

One native 262K coding-agent session runs without crossing the host pressure
guard, while retaining bounded KV capacity and the PLE mmap path.

## Actual

The percentage-based CUDA allocator consumes nearly all safe unified-memory
headroom before request-time PLE page faults and JIT work.

## Root Cause

`gpu-memory-utilization=0.85` sizes KV from CUDA-visible unified memory rather
than the appliance's host reserve. The resulting 17.08 GiB KV allocation is
larger than this single-Spark workload needs and leaves only the emergency
floor available.

Generation 6 proved that KV headroom alone is insufficient: the same request
left 13,806,878,720 bytes available but PLE demand paging produced 18.18% full
PSI and the global 10% PSI rule stopped the engine. Full PSI is therefore not
a valid emergency signal for this mmap workload even when the hard memory
floor is healthy.

## Fix

Replace percentage-based KV sizing with an explicit 12 GiB declarative cache.
This preserves more than one full 262K-token session of measured KV capacity
while returning about 5 GiB of working headroom to the host. Re-run the same
fresh agent request and verify no emergency record is emitted. Retain the 8
GiB hard available-memory backstop, but set the declarative full-PSI emergency
threshold to its disabled ceiling because PLE page faults intentionally raise
that metric while the host still has safe memory.
