# BUG-20260525-2351: `Snapshot.raw.activity_label` is permanently `Idle` under normal operation — FTRL classifier never gets training signal outside manual `sy power profile <arm>` pins

## Summary
The `OnlineClassifier` in `src/power/activity.rs` is zero-initialised (`classes: [FtrlClass::new(); 5]`). With all weights zero, every per-class sigmoid returns 0.5; argmax breaks the 5-way tie by picking index 0 (`ActivityLabel::Idle`) per the documented "argmax-of-ties" contract (`activity.rs:182, :208`). The only call site that ever invokes `partial_fit` is `daemon::one_tick` at `src/power/daemon.rs:857-861`, gated on `labels::extract_label(&entry).is_some()`. `extract_label` (`src/power/labels.rs:70`) ONLY produces a label when the audit entry's reason chain contains a `pin:<arm>` prefix — i.e. a manual `sy power profile <arm>` override. Under normal autonomous operation the user never pins anything, the classifier never partial-fits, and `Snapshot.raw.activity_label` is `Idle` for every row written to telemetry. Concretely: 262,792 of 262,792 rows across 6 days of telemetry (5/20-5/25) are labelled `idle`, including hours where the user was clearly coding or browsing. The activity channel in the bandit's context vector (Step 29's `sanitise_context_with_activity`) is therefore a constant for the entire onboarding window AND for steady-state post-onboarding operation, defeating its purpose.

## Expected
1. Under normal operation (no manual pins), `Snapshot.raw.activity_label` reflects what the user is actually doing — distribution across `Idle / Browse / Call / Code / Build` matches observed feature patterns.
2. The FTRL classifier receives self-supervised partial-fit updates from at least one production-reachable signal: either
   - the `applied_arm` itself (treating the policy's arm pick as a weak label), OR
   - the SPEC §29 "throttle / drain-residual" paths the labels.rs comment promises, OR
   - the rules-baseline state → activity mapping (COOL_AC=browse → ActivityLabel::Browse, WARM_AC=code → Code, MEETING=call → Call, etc.).
3. The bandit's context vector's activity channel is not a constant — at minimum, it varies across shield-state transitions.

## Actual
1. Six days of telemetry: every single one of 262,792 rows is `activity_label=idle`. Not a statistical skew — a hard 100%.
2. FTRL classifier has never had `partial_fit` called on this host (user has never issued `sy power profile <arm>`).
3. `sanitise_context_with_activity` (`src/power/daemon.rs:508-512`) pushes a constant value onto the bandit's context, neutralising the channel.
4. When the GRU trainer eventually fires on day 14 it reads `entry.applied_arm` (not `activity_label`) for labels, so the trainer itself isn't blocked — but the bandit's runtime context vector remains crippled, and any downstream consumer that reads `activity_label` (audit replay via `sy power explain`, `report`, the ML drift detector if it ever switches to activity-residual) sees the constant.

## Root Cause
- **Step 29 ships the consumer (context vector + audit field) without the producer (the partial_fit driver).** The `labels::extract_label` PR landed only the `pin:<arm>` path; the comment at `labels.rs:14-19` documents the gap as deferred to "Step 31+", but Step 31 (drift detection) landed without filling it.
- **No fallback / bootstrap supervision.** The FTRL classifier has no warm-start mechanism (no on-disk persistence — see BUG-20260525-2353), no rules-baseline-driven self-supervision, and no shield-state-to-label mapping. So in the absence of pins it stays at the zero-initialised "everything is idle" attractor forever.

## Fix
1. **Add a rules-baseline-derived self-supervision path to `labels::extract_label`.** Map the source label written into the reason chain by `daemon.rs:783-808` onto an `ActivityLabel`:
   - `onboarding-baseline:browse` → `Browse` (low confidence weight, e.g. 0.25 — the baseline isn't ground truth but it's better than no signal)
   - `onboarding-baseline:code` → `Code`
   - `onboarding-baseline:idle` → `Idle`
   - `onboarding-baseline:call` → `Call`
   - `onboarding-baseline:whisper` → `Idle` (whisper is a power profile, not an activity)
   - `bandit:<arm>` → ditto, weight 1.0 (post-onboarding the bandit's pick is the strongest signal we have short of a manual pin)
   - `drift-baseline:*` → same as onboarding-baseline (drift fell back to rules)
2. **Extend `labels.rs::extract_label` and update `daemon.rs:857-861`** to honour the weighted partial_fit (the existing `if weight > 0.0` gate already handles this — the only change needed is producing a non-None Option from the rules-baseline reason path).
3. **Tests:**
   - `src/power/labels.rs::tests::extracts_browse_from_onboarding_baseline_reason` — assert `extract_label(entry with reason_chain[0]="onboarding-baseline:browse")` returns `Some((Browse, 0.25))`.
   - `src/power/labels.rs::tests::extracts_code_from_bandit_reason` — assert `Some((Code, 1.0))` for `bandit:code (ucb=0.42)`.
   - `src/power/labels.rs::tests::weight_zero_signals_skip_partial_fit` — confirm the existing `weight > 0.0` gate is still honoured.
   - Integration: `tests/power_classifier_learns_from_telemetry.rs` — replay a synthetic 100-row NDJSON through `daemon::one_tick`, assert the classifier's per-class weight vector is non-zero for at least 2 classes after the replay.
4. **Telemetry probe** (manual, post-fix): after one day of operation, `cat ~/.local/state/sy/power/telemetry-$(date +%F).ndjson | jq -r '.snapshot.raw.activity_label' | sort | uniq -c` must show ≥ 2 distinct labels.
