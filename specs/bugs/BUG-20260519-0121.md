# BUG-20260519-0121: sy.target never starts at login (memory plane absent after reboot)

## Summary
`sy.target` has no `[Install]` section, so `systemctl --user enable sy.target` registers it as `linked` without dropping a symlink into `default.target.wants/`. After reboot the user manager never activates `sy.target`, so none of the services symlinked under `sy.target.wants/` (sy-agentd, sy-knowledge, sy-qdrant) come up.

## Reproduction
- Method: failing test (file-content assertion proves the unit is non-installable)
- Test: `tests/systemd_unit_sy_target_installable.rs::sy_target_has_install_section_with_wantedby`
- Command: `cargo test --test systemd_unit_sy_target_installable`
- Evidence on live host (Fedora 43, user@1000):
  - `systemctl --user list-unit-files 'sy*'` → `sy.target  linked  disabled`
  - `ls ~/.config/systemd/user/default.target.wants/` → only `syauth-presenced.service`; no `sy.target` symlink
  - `systemctl --user show sy.target -p WantedBy` → `WantedBy=` (empty)
  - `systemctl --user list-units 'sy*'` after fresh boot → only `sy-stack-bar.service` (it has its own `WantedBy=graphical-session.target` and rides the niri session)

## Expected
After `sy apply` + reboot, `sy.target` is pulled up by `default.target`, and the `Wants=sy-agentd sy-knowledge sy-qdrant` directives plus the `sy.target.wants/` symlinks bring the whole memory plane up.

## Actual
`sy.target` stays inactive. `sy-agentd`, `sy-knowledge`, `sy-qdrant` never start. User can't search the knowledge index, agents have no embeddings/rerank, and `sy agt run` fails until the user manually `systemctl --user start sy.target`.

## Root Cause
`configs/systemd/user/sy.target` only contains `[Unit]` with `PartOf=graphical-session.target` and `After=graphical-session.target`. Two problems:

1. **No `[Install]` section** — `systemctl --user enable sy.target` cannot drop a `default.target.wants/sy.target` symlink, so the user manager has nothing to pull the target up at login. It reports `linked  disabled` and stays inactive.
2. **`PartOf=` is stop-only** — it propagates STOP from `graphical-session.target` down to `sy.target` (correct teardown behaviour), but it does NOT start `sy.target` when `graphical-session.target` activates. Standard systemd semantics: only `Requires=`, `Requisite=`, `Wants=`, `BindsTo=` on the upstream side, or `WantedBy=`/`RequiredBy=` on the downstream side, cause start propagation.

The result is a unit that's perfectly happy to be torn down with the session but never wired in to start with it.

`sy apply` (`src/supervision/apply.rs`) also never enables the target — it only `daemon-reload`s after symlinking unit files. So even with the `[Install]` section added, the user must remember to `systemctl --user enable sy.target`. Productized install must enable it automatically.

## Fix
1. Add `[Install] WantedBy=default.target` to `configs/systemd/user/sy.target`. `default.target` is the user-manager root (activated by `user@.service`) — choosing it over `graphical-session.target` keeps the memory plane available in non-graphical user sessions (SSH, recovery) and avoids the niri-session-readiness race for boot-time activation.
2. Wire `sy apply` to call `systemctl --user enable sy.target` after `daemon-reload` so the install is idempotent and one-shot.

## Traceability
- Failing test: `tests/systemd_unit_sy_target_installable.rs`
- Fix: `configs/systemd/user/sy.target` (added `[Install]`), `src/supervision/apply.rs` (enable hook)
