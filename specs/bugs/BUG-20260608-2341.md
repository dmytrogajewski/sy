# BUG-20260608-2341: sy-powerd runs with an empty arm table — power.toml not found as a service

## Summary
`sy-powerd` resolves `configs/sy/power.toml` relative to the process
cwd, but the systemd `--user` unit sets no `SY_ROOT` and no
`WorkingDirectory`, so cwd is `$HOME`, the file isn't found, and the
daemon silently falls back to `PowerConfig::default()` — whose
`arms` is **empty**, leaving the contextual bandit with no profiles to
learn over.

## Reproduction
- Method: test + manual
- Test: `src/power/mod.rs::tests::resolve_power_config_path_falls_back_to_xdg`
  — the pure resolver must return the installed XDG path (not a
  nonexistent cwd-relative path) when `SY_ROOT` is unset and the cwd
  has no `configs/`.
- Manual evidence:
  - `journalctl --user -u sy-powerd` → "checkpoint schema or arms-hash
    mismatch, re-learning from zero".
  - The service-written checkpoint (`checkpoint.json`, saved by
    `sy-powerd`) carries `bandit.arms: []` and `arms_hash:
    8928969220429462997` (the hash of an empty arm set).
  - A daemon run with cwd = repo loads the real 8 arms
    (`whisper/idle/browse/call/code/build/npu-burst/flat-out`,
    `arms_hash: 9900873153431424971`) — proving the table only loads
    when `configs/sy/power.toml` is reachable from cwd.
  - `ls /home/dmitriy/configs/sy/power.toml` → ENOENT (the path the
    service actually probes); the unit has no `SY_ROOT`/`WorkingDirectory`.

## Expected
The daemon (and `sy power` CLI / status) loads the configured arm table
no matter the cwd, and `sy power apply` installs `power.toml` to a stable
location so a fresh machine reproduces the full config declaratively
(no snowflakes).

## Actual
Run as the `--user` service, the daemon loads zero arms; the bandit can
never learn a power policy, and every checkpoint is rejected on the next
restart whenever the (empty vs real) arm hash flips.

## Root Cause
Three duplicated resolvers (`daemon.rs::power_config_path`,
`cli.rs::config_path`, `status.rs::live_onboarding_hint`) all did
`SY_ROOT ? $SY_ROOT/configs/sy/power.toml : configs/sy/power.toml`
(cwd-relative). There was no installed-config path in the precedence and
`sy power apply` never wrote `power.toml` (it installs the unit, polkit,
udev, etc. via `include_str!`, but not the config). The unit runs with
cwd `$HOME`, so the cwd-relative branch always missed.

## Fix
1. **Unified resolver** `power::power_config_path()` with CLAUDE.md
   precedence: `SY_ROOT` → cwd `configs/sy/power.toml` *if it exists*
   (dev-from-repo) → `$XDG_CONFIG_HOME/sy/power.toml` (else
   `$HOME/.config/sy/power.toml`). The pure inner `resolve_power_config_path`
   is unit-tested for all three branches. `daemon.rs`, `cli.rs`, and
   `status.rs` now call the shared resolver; the daemon's intent
   whitelist is derived from its parent dir (matching the CLI).
2. **Installer** embeds `configs/sy/power.toml` + `configs/sy/intent_whitelist.toml`
   and writes them to `<config_root>/sy/` (`~/.config/sy/`) via the same
   idempotent `write_if_changed` path used for the unit. `sy power apply`
   now materialises the config the service reads.

## Verification
- `sy power apply` writes `~/.config/sy/power.toml`; restarting
  `sy-powerd` then loads the 8-arm table (verified via `sy power status
  --json` / `sy power list-profiles`).

## Traceability
- Failing test: `src/power/mod.rs::tests::resolve_power_config_path_falls_back_to_xdg`
- Fixed in: `src/power/mod.rs` (resolver), `src/power/daemon.rs`,
  `src/power/cli.rs`, `src/power/status.rs`, `src/power/apply/installer.rs`
  (+ `apply_opts` config_root wiring in `cli.rs`)
