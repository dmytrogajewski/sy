# BUG-20260829-1148: verified PLE reuse exhausts the startup memory floor

## Summary

The single-Spark SGLang profile verifies and serves the durable PLE artifact,
but its validation scan leaves avoidable page-cache pressure and its automatic
hybrid-cache split allocates more recurrent-state slots than one configured
MTP request needs.

## Reproduction

- Method: real-device lifecycle reproduction plus image-contract tests.
- Test: `tests/spark_engine_image_contract.rs::persistent_mmap_images_reclaim_validation_page_cache`.
- Command: `sy spark dgx-spark serve qwen3.8:flash-next --name qwen38-sglang-qualification --detach --json`.
- Evidence: generation 13 reused and SHA-256 verified the 51,200,245,760-byte
  PLE artifact, loaded 84.08 GiB of target weights and 0.87 GiB of MTP
  weights, allocated 21 Mamba slots and a 254,592-token KV pool, then reached
  8,071,848 KiB `MemAvailable` during the complete 32K prefill-shape warmup.
  This is below the strict 8 GiB floor and worse than generation 12's
  8,364,244 KiB sample. The resource guard stopped the container before any
  user generation; it was not OOM-killed and did not restart.

## Expected

An exact durable artifact is fully verified without retaining the sequential
verification scan in page cache, and a one-request MTP profile avoids persistent
per-draft recurrent snapshots while retaining a real 262,144-token pool.
The complete warmup and first generation remain above the 8 GiB floor.

## Actual

The PLE checksum reader streams the whole 47.7 GiB artifact without page-cache
reclaim advice. SGLang's automatic `mamba_full_memory_ratio=0.9` gives this
one-request profile 21 recurrent-state slots even though `extra_buffer` with
overlap needs five base slots and four MTP intermediate slots. The automatic
KV allocation is only 254,592 tokens despite the declared 262,144-token
context.

## Root Cause

`--weight-loader-drop-cache-after-load` applies
`posix_fadvise(DONTNEED)` only to safetensors checkpoint shards; the custom PLE
verification reader is outside that loader. Linux documents
`POSIX_FADV_NOREUSE` for one-pass mapped-file scans and
`POSIX_FADV_DONTNEED` for releasing clean cached pages after streaming.

The pinned SGLang sizing contract defines five recurrent-state slots per
request for `extra_buffer` with overlap, plus one intermediate recurrent state
per speculative draft token. With ordinary recurrent verification, one request
and four draft tokens cost nine slot-equivalents. The pinned ReplaySSM
spec-verify path instead stores the four draft inputs in a small exact-fold ring,
so its formula is `S + D = 5 + 0`: five persistent slots and no per-draft SSM
snapshot. It keeps the FP32 checkpoint bit-identical to recurrent verification.

## Fix

A content-addressed image transformer keeps the full SHA-256 verification but
advises `POSIX_FADV_NOREUSE` before the scan and `POSIX_FADV_DONTNEED` after it.
Its image self-test proves the digest is unchanged and both advice calls bracket
the scan. The declarative profile enables the pinned engine's closed-loop
ReplaySSM spec-verify path, pins `--max-mamba-cache-size 5`, and retains
`--max-total-tokens 262144`; reasoning, the three-step/four-draft MTP chain,
`extra_buffer`, overlap, decode graphs, and the complete 32K warmup remain enabled.

The real-device acceptance run must report exactly five persistent state slots,
no intermediate SSM snapshot, and 262,144 total tokens; stay robustly above the floor through first generation,
and pass a warm stop/start cycle. A merely bootable profile or one that silently
shrinks the pool is not accepted.

Generation 15 proved the corrected persistent-cache and pool identities but
still reached one 8,276,612 KiB `MemAvailable` sample during the final 32K
warmup bucket, 111,996 KiB below the strict floor. The guard stopped it before
semantic readiness; swap-in and full-memory PSI remained zero, Docker reported
zero restarts and no OOM kill, and the instance was removed. SGLang's own
[tuning guide](https://github.com/sgl-project/sglang/blob/main/docs/docs/advanced_features/hyperparameter_tuning.mdx)
identifies `--chunked-prefill-size` as the prefill activation-memory control.
Generation 16 evaluated a 512-token chunk without changing the content-addressed
image or cache epoch. It completed the 32K warmup, but normal semantic readiness
then drove `MemAvailable` through 8,207,140 KiB to 8,123,648 KiB. The guard
removed the container with zero Docker restarts and no OOM kill before any user
generation. The smaller chunk did not improve the acceptance floor and is
therefore rejected; the profile retains the original 1,024-token chunk while
the persistent draft-KV, recurrent-state, and graph allocations are investigated.

Generation 18 retained the 1,024-token chunk and proved the expected 262,144
target/draft token allocation, five ReplaySSM state slots, reasoning, MTP 3/4,
and decode graphs, but runtime PLE accesses repopulated reclaimable file cache
through the complete warmup. The candidate was stopped without a user request;
FP8 KV was rejected because this checkpoint has no calibrated K/V scales and
the pinned runtime would otherwise use unit scales.

The final content-addressed image adds a config-gated post-warmup cleanup that
awaits every declared prefill shape, verifies the allocator is idle, and calls
the existing transient cache flush without changing persistent KV, ReplaySSM,
CUDA graphs, MTP, reasoning, or host caches. Generation 19 completed all 18
shapes through 32K, logged `Post-warmup transient allocator state flushed`,
and reached semantic readiness with a 9,014,548 KiB minimum `MemAvailable`.
It then completed a real reasoning-enabled managed generation in 1.337 seconds
(63 input, 36 output, 99 total tokens), remained healthy with zero restarts and
no OOM, and held only 1,163,415,552 bytes (2.27%) of the PLE inode resident.
