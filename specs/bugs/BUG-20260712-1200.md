# BUG-20260712-1200: `call_active` is a one-tick pulse, not level state — logind watcher de-dups the held inhibitor

Related: **BUG-20260712-1201** (MEETING shield state absorbing). The two
share the call-detection path and were fixed as one change: the DFA's
MEETING release (1201) depends on `call_active` being a faithful level,
which this bug (1200) restores.

## Summary
`src/power/intent/logind.rs` — `LogindChannel::poll()` treated a held
idle-inhibitor as an EDGE: a `last_emitted` de-dup returned
`CallActive` only on the grab tick, then `None` on every subsequent
tick while the lock was still held. But `snapshot::drain_intent` (and
every downstream consumer) reads the poll result as a LEVEL each tick —
`raw.call_active = poll() matched CallActive this tick`. The mismatch
made `call_active` a single 1 Hz pulse instead of a level that tracks
the inhibitor's full lifetime.

## Reproduction
- Method: live host probe (2026-07-12).
- Command: `systemd-inhibit --what=idle --who=zoom sleep 12`.
- Observed telemetry (`sy power status --json` polled at 1 Hz):
  `call_active` went `true` for exactly ONE tick (~0.8 s after the
  grab), then `false` on the very next tick while the inhibitor was
  still held for 11 more seconds. No release edge was ever observable —
  the signal had already dropped long before the actual release.
- Source trace: `poll()` called `poll_bus()` (level: `Some(CallActive)`
  while a whitelisted `idle` inhibitor is listed), then folded it
  through a `last_emitted: Option<String>` de-dup that suppressed the
  event whenever `who` equalled the previously emitted `who`. So tick 0
  emitted, tick 1..N (same `who`) returned `None` → `drain_intent` set
  `call_active = false`.

## Expected
Per sy-power ROADMAP Step 5 R1 + SPEC §2/§4: `call_active` reflects the
LEVEL — `true` for every tick a whitelisted idle-inhibitor is held,
`false` the tick it is released.

## Actual
`call_active` was `true` for a single tick on the grab edge, then
`false` for the rest of the call. The MEETING shield state (which keys
off `call_active`) therefore only latched because of a *separate*
absorbing bug (BUG-20260712-1201); the underlying call signal itself
was already gone after one tick.

## Root Cause
`LogindChannel::poll` carried edge-detection state (`last_emitted`) that
was semantically wrong for a level consumer. The de-dup was added to
avoid "re-firing every tick", but the daemon *wants* the value every
tick — it re-derives `call_active` from scratch on each `drain_intent`.

## Severity / Impact
High. Silently defeats every call-aware behaviour: the MEETING shield
rung, the `call_active` bandit-context channel, and the GRU "call"
activity class all saw a 1-tick blip instead of the true call duration.
No crash, no log signal.

## Fix
`LogindChannel::poll` is now a pure level read: it lists the currently
held inhibitors every tick via a new `InhibitorSource` seam and returns
`CallActive` whenever a whitelisted `idle` inhibitor is present, `None`
otherwise. The `last_emitted` de-dup and `poll_bus` are removed. The
`InhibitorSource` trait abstracts the `zbus` `ListInhibitors` round-trip
(`ZbusInhibitorSource` in production) so the level semantics are
testable without a live system bus. A transient bus error degrades to
`None` (no lock held) rather than latching the previous value.
