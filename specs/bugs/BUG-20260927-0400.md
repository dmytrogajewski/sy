# BUG-20260927-0400: every orderly worker shutdown ends in SIGSEGV inside the VitisAI EP finalizer

## Summary

`systemctl --user restart sy-knowledge.service` (or `stop`) dumped **two**
core files — one per live worker, ~330 MB per restart — and journald recorded
`status=11/SEGV` for the unit. An orderly shutdown was indistinguishable from
a crash, `sy doctor`'s `coredump.recent_count` could never return to `pass`
while the plane was in use, and on a root fs at 92 % the retained cores were
real disk. Every restart since the VitisAI EP first loaded did this.

## Reproduction

```bash
coredumpctl list | grep "$(readlink -f ~/.local/bin/sy)" | wc -l   # note N
systemctl --user restart sy-knowledge.service; sleep 15
coredumpctl list | grep "$(readlink -f ~/.local/bin/sy)" | wc -l   # N + 2
coredumpctl info <newest-pid>            # Command Line + stack trace
```

Before the fix: +2 cores per restart (`--kind embed` ≈ 240 MB,
`--kind rerank` ≈ 64 MB), newest core timestamp inside the stop window.

## Expected

A worker that finishes its serve loop exits with a status code.

## Actual

Both workers died on signal 11 while *leaving* `main`. Captured trace
(thread 75401, `sy aiplane worker --kind rerank`):

```
#0  libonnxruntime_providers_vitisai.so + 0x1d78e
#1  libonnxruntime_providers_vitisai.so + 0xf4b8
#2..#6  libonnxruntime.so.1.23.3            (session / EP teardown)
#7..#9  sy                                  (ort destructor)
#10 _dl_call_fini      <-- shared-object finalizers, not our code
#11 _dl_fini
#12 __run_exit_handlers
#13 exit
#14 __libc_start_call_main
```

## Root Cause

AMD's VitisAI execution provider registers a library finalizer that
dereferences ONNX Runtime state already destroyed by the time the dynamic
linker runs `DT_FINI` handlers — after `main` has returned. Two consequences
that make this easy to fix wrongly:

1. It is **not** our `unload()` (that runs earlier and completes), and it is
   not the cold VAIP compile — the earlier `BUG-20260927-0119` notes mistook
   these cores for prep-time `SIGABRT`s from the Python side, which are a
   separate, genuinely prep-side event (`python` cores in the same window).
2. **`std::process::exit()` does not help.** It routes through the same
   `exit()` → `__run_exit_handlers` → `_dl_fini` path, so the intuitive fix
   still dumps a core and still reports signal 11.

## Fix

`aiplane::worker::exit_process(status) -> !` terminates via `libc::_exit`,
which skips userspace teardown while the kernel still releases the session,
the `/dev/accel` mappings, the socket fd and every page. Ordering in `run()` is
what makes that safe — in sequence: log the terminal state (error-level when
the serve loop failed), `workload.unload()` so the NPU is handed back *before*
the process disappears (a respawn must not queue behind our teardown), unlink
the socket, `drop(_obs_guard)` to flush the journald/JSONL appenders, then
`_exit(0|1)`. `run()` now documents that it never returns once the IPC server
is up, and the supervisor is unaffected because it decides on liveness
(`try_wait`), never on exit codes.

Also in this file, per the project's unsafe rule: the pre-existing
`install_signal_handlers` `unsafe` block gained its required justification
comment (a handler that only stores to a static `AtomicBool`).

## Verification

- **Zero** new cores across restarts whose workers ran the fixed binary
  (`before=11 after=11`), and **zero** `status=11/SEGV` lines in journald for
  those stops; the two cores that did appear belonged to pre-fix workers dying
  during the transition restart, and the immediately following restart of the
  same (now fixed) workers produced none.
- `tests/aiplane_worker_exits_without_sigsegv.rs`: SIGTERM shutdown exits 0
  (not signalled) and unlinks its own socket, in a sandboxed `HOME` so
  `/dev/accel` is untouched; `npu_worker_shutdown_does_not_segfault` covers
  the real EP path behind `test-npu`. The faulting finalizer only exists once
  the EP is loaded, so the hermetic tests guard the shutdown *contract* the
  fix relies on rather than reproducing AMD's bug.

## Follow-ups (not in this fix)

- The 11 retained cores (~1.9 GB) need privileged removal
  (`sudo coredumpctl --delete --all`); nothing else is left behind, and
  `systemd-tmpfiles` ages that directory regardless. `doctor`'s warn is a
  rolling 24 h window, so it clears on its own now that crashes have stopped.
- The defect is AMD's and should be filed upstream with the trace above; sy
  can only decline to run their finalizer.
- `run()` could stop calling `unload()` entirely now that `_exit` releases the
  device anyway; kept because it hands the NPU back before the process is
  gone, which shortens the next worker's path to `Ready`.
