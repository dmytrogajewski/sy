# BUG-20260827-2215: text-only GGUF is forced through vision health probe

## Summary

Serving a GGUF without a projector fails because the selected engine profile
publishes vision independently of the installed model artifact's capabilities.

## Reproduction

- Method: manual real-device reproduction plus unit regression test
- Test: `spark::engine::tests::text_only_artifact_does_not_publish_engine_vision`
- Command: `sy spark dgx-spark serve ornith-1.5:9b-q4-k-m --name eval-ornith9-q4 --json`
- Evidence: serve exited 5 with `engine semantic capability contract failed:
  vision probe rejected with HTTP 5xx`; llama.cpp reported `image input is not
  supported ... you may need to provide the mmproj`.

## Expected

The effective gateway capabilities are constrained by both the engine profile
and the installed artifact. A text-only GGUF starts with text protocol probes
and does not advertise or probe vision.

## Actual

`EnginePolicy::gateway_profile_for` copied the generic llama.cpp profile's
vision policy even when the artifact advertised only text generation and had no
projector.

## Root Cause

`EnginePolicy::gateway_profile_for` copied the selected engine profile's vision
capability and policy without checking the installed artifact's declared
modalities. The llama.cpp generic profile correctly describes engine-level
vision support, but a primary-only GGUF cannot exercise that support.

## Fix

Constrain vision publication to artifacts that declare vision. Generic
text-generation and tool-call protocol support remains available. Add the
official publisher-owned Ornith 9B Q4_K_M artifact and BF16 projector to the
declarative model catalog with reasoning, text-generation, tool-calling, and
vision capabilities. Primary-only ad-hoc GGUF downloads still remain text-only.

## Traceability

- Failing test: `src/spark/engine.rs::tests::text_only_artifact_does_not_publish_engine_vision`
- Fixed in: `src/spark/engine.rs`, `configs/sy/spark/models.toml`,
  `src/spark/model_catalog.rs`
