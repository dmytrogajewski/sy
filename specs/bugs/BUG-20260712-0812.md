# BUG-20260712-0812: `tuned.service` is a second, unmanaged writer for EPP / `platform_profile` — silently undoes `sy-powerd` actuator writes

## Summary
On the audit host (2026-07-12) `tuned.service` is **active** while
`sy-powerd.service` is **enabled**, and `tuned-ppd.service` is inactive.
`tuned` and `sy-powerd` both write the same sysfs knobs — the per-policy
`energy_performance_preference` (EPP) files and
`/sys/firmware/acpi/platform_profile`. Two writers for one knob means
`tuned` can rewrite EPP / `platform_profile` underneath `sy-powerd` at
any time, silently reverting the daemon's bandit-chosen arm. `tuned` was
never brought under `sy`/`configs/` management, so leaving it running is
a snowflake risk (CLAUDE.md core rule: every environment actor must be
productivised, and `sy` must be the single source of truth). No roadmap
step covered `tuned`; this documents Task S7, which adds declarative
ownership.

## Reproduction
- Method: live `systemctl` probe on the audit host (2026-07-12).
- Live evidence:
  ```
  systemctl is-active  tuned.service       = active
  systemctl is-active  tuned-ppd.service   = inactive
  systemctl --user is-enabled sy-powerd.service = enabled
  ls /usr/lib/systemd/system/tuned.service  # present (Fedora `tuned` pkg)
  ```
- Overlap: `src/power/apply/epp.rs` writes each
  `devices/system/cpu/cpufreq/policy*/energy_performance_preference`;
  `src/power/apply/platform.rs` writes
  `firmware/acpi/platform_profile`. `tuned`'s active profile plugins
  drive the exact same nodes.

## Expected
`sy` should own EPP / `platform_profile` uncontested when `sy-powerd`
is the declared governor. The competing writer must be surfaced
(observability) and disabled **declaratively** through `sy power apply`
— never via an ad-hoc `systemctl disable tuned` on the host (that would
be a snowflake).

## Actual
`tuned` runs unmanaged alongside `sy-powerd`. `sy doctor` had no check
for the conflict, and `sy power apply` did not plan disabling it, so an
operator had no reproducible, in-repo way to resolve the two-writers
race.

## Root Cause
The `sy-power` roadmaps productivised the PPD conflict
(`power-profiles-daemon`, Step 37 mask path) but not `tuned`, the other
Fedora governor that writes the same knobs. `tuned` fell outside the
declarative surface entirely.

## Severity / Impact
Moderate. Not a safety issue (the crash-safe vendor-default handoff is
unaffected), but a correctness / reproducibility defect: the daemon's
actuator writes can be silently reverted by `tuned`, and the fix
previously required a manual host change that `sy apply` would not
reproduce on a fresh machine.

## Fix (Task S7)
Declarative ownership, mirroring the PPD (Step 37) pattern:
1. **`sy doctor` check `power.tuned_conflict`** (`src/doctor/checks.rs`):
   FAIL when `tuned.service` or `tuned-ppd.service` is active while
   `sy-powerd.service` is enabled — names the conflict ("two writers for
   EPP/platform_profile") and the remediation (`sy power apply` plans
   disabling+masking tuned). Skips when `sy-powerd` is not enabled or
   `systemctl` is absent; passes when no competing writer is active.
2. **`sy power apply` / installer** (`src/power/apply/installer.rs`):
   `handle_tuned_conflict` detects an installed `tuned` unit
   (`default_tuned_unit_paths`) and, gated on the usual `--yes`
   confirmation, PLANS a system-wide `systemctl disable --now
   tuned.service` + `systemctl mask tuned.service`. Shows in the
   `--dry-run` diff as `Updated(<system_unit_root>/tuned.service)`;
   idempotent (a second apply against the already-masked host surfaces
   `AlreadyMatches` and does not re-invoke systemctl); requires root
   (the mask link lives in the root-owned system unit dir — the runbook
   runs `sy power apply --yes` under root). Without `--yes`, the
   installer emits an advisory Warning instead of touching unit state.

Actual host application lands via the operator runbook (privileged
`sy power apply --yes`), not from this change set.

## Notes
Filed from Task S7. Unlike PPD there is no `--with-ppd`-style
co-existence opt-out: two writers for one knob is always a defect, so
the only choices are "mask it" (`--yes`) or "not yet" (advisory).
