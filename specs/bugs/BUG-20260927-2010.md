# BUG-20260927-2010: bulk embedding jumped the queue it was supposed to stand in

## Summary

`aiplane.batch` was dispatched straight to the workload backend, and the
knowledge plane's own index pass called `Supervisor::run_batch` in-process.
Neither went through the strict-priority scheduler: no per-class admission
(`SPEC §4.3`), no queue caps, no `Realtime > Interactive > Background > Batch`
ordering, no `Overloaded` backpressure, no entry in `Status.queue_depths`, and
no inflight record for `aiplane.cancel`. A bulk embed was invisible to the
component whose entire job is deciding who uses the NPU next.

The root cause was structural rather than an overlooked call:
`scheduler::Request` carried exactly one `WorkloadInput` and answered one
`WorkloadOutput`, so a batch **had no representation admission could accept**.

## Reproduction

- Method: automated, deterministic (a gate in the fake backend parks the
  dispatcher so ordering needs no wall-clock assumptions).
- Command: `cargo test --bins -- ipc::tests::batches_are_admitted_by_priority`
- Evidence, against the pre-fix dispatch restored temporarily:

  ```text
  thread '…batches_are_admitted_by_priority' panicked at src/aiplane/ipc.rs:3159:13:
  batches must wait behind admission, reached backend:
  ["bg-batch-a", "bg-batch-b", "bg-batch-a-2", "bg-batch-b-2",
   "interactive-batch", "interactive-batch-2"]
  ```

  While the dispatcher was parked, three admitted batches had already reached
  the backend — and the `Interactive` one ran **last**, which is what an
  unadmitted path looks like: arrival order, not priority.

## Expected

SPEC §4.3: every request that consumes the single-context device is admitted
by class. `sy aiplane status --json` reports the pressure, `queue_caps` means
something, and a foreground `knowledge_search` is not racing a 700-file embed
pass for the device.

## Actual

- `Status.queue_depths` could never show a batch, so scheduler pressure from
  the largest consumer in the system was unobservable.
- The only thing protecting search latency during an index pass was
  `EMBED_IPC_MAX_CALL = 64` — a caller-side courtesy, not a policy. It is
  cited verbatim in its own doc comment as a workaround for the missing
  admission: *"an unbounded batch would park a 25 MB Telegram export's whole
  chunk list on the NPU and starve a foreground `knowledge_search`"*.
- `sy aiplane cancel <request_id>` could not resolve a batch's workload kind,
  because `inflight_kinds` mirrors the scheduler the batch never entered
  (`aiplane.run` registered; `aiplane.batch` did not).
- The daemon's own pass (the ~700-file scheduled sweep, i.e. the common case)
  was the *worst* offender: it never crossed IPC at all.

## Root Cause

Two entry points diverged because the trait offered two methods.
`AiplaneDispatch::run` sat behind the scheduler and
`AiplaneDispatch::batch` did not, and nothing in the types said which one a
new caller should reach for. `Request`'s single-input shape made the asymmetry
look deliberate — a scheduler for single calls — when the backend had been
batch-shaped (`Supervisor::run_batch`) since Step 1.

## Fix

- **`scheduler::Request` carries `Vec<WorkloadInput>` and answers
  `Vec<WorkloadOutput>`.** `aiplane.run` is a batch of one. The dispatcher now
  has a single backend call to make, and every request on the plane is
  admitted by class.
- **`AiplaneDispatch::run` deleted** (dead, and the thing that made the split
  look intentional). One method, `batch`, so there is no unadmitted door left
  to walk through.
- **`handle_aiplane_batch` admits.** Same `SchedRequest::new` →
  `Scheduler::admit` path as `aiplane.run`, so it inherits caps, ordering,
  `Overloaded` (with its `retry_after_ms`), cancellation, and the hard-escape
  watchdog. It also registers in `inflight_kinds`, restoring cancel-by-id.
- **New `InflightKindGuard`** (RAII) replaced four hand-rolled
  lock-insert/lock-remove sequences in the run handler; both handlers now
  cannot leak an entry on any exit path, including `?`-style early returns.
- **New `ipc::admit_blocking_batch`**, and `embed::embed_batch` uses it for
  the plane-owning route — closing the in-process bypass. Direct
  `Supervisor::run_batch` survives only as the documented "scheduler not
  installed yet" fallback that `embed_one` already used.
- **Bulk embedding admits at `Background`, not `Interactive`.** A batch is bulk
  work by definition; the latency-sensitive path is `embed_one`. Asking for
  `Interactive` would have put an index pass in the same class as the searches
  it must defer to.
- **Adaptive group size (`shrink_group`), because admission makes a pass
  preemptible *in principle*.** A `Background` inflight older than
  `HARD_ESCAPE_THRESHOLD` (200 ms) is cancelled when an `Interactive` request
  queues. On `Cancelled`/`Overloaded` the group halves; at the one-chunk floor a
  group is below the escape threshold and cannot be preempted, so progress is
  guaranteed and the pass degrades instead of failing. Only at the floor does
  the pass give up, with a message that names the cause.
  **Honest scope: this retry has never fired in the field.** An ONNX call
  cannot be aborted mid-flight, so the watchdog's cancel is delivered but the
  worker runs the group to completion and answers normally — `embed_batch`
  sees `Ok`, not `Cancelled`, and the pass log recorded no cancel or overload
  events across a 512-chunk run. It is defensive code, unit-tested, and it is
  what keeps a pass alive the day a worker does gain a cancellable call.
- **`EMBED_IPC_MAX_CALL` 64 — 8, derived instead of asserted.** Because the
  worker cannot be interrupted mid-group, *the group size and not the watchdog*
  is what bounds a search's wait behind a pass. It is now
  `HARD_ESCAPE_BUDGET_MS / EMBED_CHUNK_COST_MS` (250 / 31 = 8), with the budget
  pinned to both scheduler constants by a test, so the SPEC §4.3 promise holds
  rather than being quietly rounded up to ~2 s. A 512-chunk ladder at group
  sizes 64/16/8/4 measured 31.6-32.1 chunks/s at every size — per-chunk
  cost is flat, so batching past a handful of passages buys nothing and the
  shrink is free.
- **`sy knowledge bench` timed the wrong thing.** It sliced input by a
  hardcoded 64 and reported that as `batch_size`, so `mean_batch_ms` measured a
  client-side slice and not the dispatched group; the first ladder run looked
  flat for that reason. It now slices at `EMBED_IPC_MAX_CALL`, so the bench
  reports the quantity the QoS bound is actually about.

## Residual

- **Preemption granularity is worker-limited, and that is the real
  interactivity bound.** `Supervisor::cancel` does send `WorkerReq::Cancel` and
  poll health, but an ONNX session is not interruptible mid-call, so the escape
  watchdog can only ever reclaim a group boundary. Group size is therefore the
  enforced bound (now ~250 ms, measured 0.28 s worst-case); making it a true
  preemption needs per-batch progress reporting inside the embed worker, which
  is a VitisAI/ORT-side change and out of scope here.
- A preempted group discards its NPU work rather than resuming: the ONNX
  batch has no checkpoint. Halving bounds the waste at one group (~250 ms,
  was ~1.9 s).
- The scheduler is single-dispatcher: a batch and a search never overlap on
  the device, they interleave. Splitting the plane by workload (rerank on the
  iGPU, embed on the NPU) is the real throughput fix and is out of scope here.
- `Status.queue_depths` now includes batch pressure but nothing renders it;
  `sy aiplane status` prints the map, no tile does.
