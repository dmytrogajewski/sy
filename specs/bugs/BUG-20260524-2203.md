# BUG-20260524-2203: knowledge dead and `sy mon` reports 0 NPU workloads when qdrant has a corrupt segment

## Summary
`sy-qdrant.service` panics on startup with `Json error: EOF while parsing a value at line 1 column 0` because one shard segment has a 0-byte `vector_storage/vectors/config.json` left over from a prior ungraceful shutdown. `sy-knowledge.service` `BindsTo=sy-qdrant.service`, so systemd tears knowledge down with qdrant — and because the aiplane NPU embedder runs inside the knowledge daemon, `sy mon` then reports `npu.holders=[]` / 0 workloads on the NPU. One root cause, two visible symptoms.

## Reproduction
- Method: live-host evidence + hermetic integration test
- Test: `src/knowledge/repair.rs::tests::quarantines_segment_with_empty_vector_config` (+ siblings)
- Live-host evidence (Fedora 43, 2026-05-24 ~20:06 MSK):
  - `systemctl --user status sy-qdrant.service` → `failed (Result: exit-code)`; restart counter 6; "Start request repeated too quickly".
  - `journalctl --user -u sy-qdrant.service` (each restart):
    ```
    ERROR qdrant::startup: Panic occurred in file
      lib/collection/src/shards/replica_set/mod.rs at line 282:
      Failed to load local shard
      ".../sy_knowledge/0": Service internal error: Json error:
      EOF while parsing a value at line 1 column 0
    ```
  - `systemctl --user status sy-knowledge.service` → `inactive (dead)`; killed with SIGTERM 1 s after start (BindsTo cascade).
  - `find …/sy_knowledge/0 -name '*.json' -size 0` → exactly one hit:
    `segments/f7c39773-2a27-402e-84ed-bf19fcccc11a/vector_storage/vectors/config.json` (0 bytes).
  - `ls -A …/sy_knowledge/0 | grep -c atomicwrite` → 399 leaked `.atomicwrite*` temp directories.
  - `sy mon snapshot --json` → `"npu": {"active": false, "holders": []}`.
  - `sy aiplane status --json` → `"daemon_running": false`.

## Expected
1. The knowledge daemon's qdrant supervisor detects a segment with an empty / unparseable JSON file before qdrant boots and moves the offending segment out of the live path (quarantine) so qdrant can start.
2. The same recovery runs as `ExecStartPre=` on `sy-qdrant.service` so the systemd-managed path is covered too.
3. Stale `.atomicwrite*` directories under each shard root are swept on the same pass so they don't accumulate.
4. With a freshly quarantined segment, qdrant starts cleanly, `sy-knowledge.service` reaches `active (running)`, and `sy mon` reports `npu.holders` containing `embed` + `rerank`.

## Actual
1. Qdrant panics on the empty file; systemd restarts it 6× in 100 ms and then stops trying.
2. `BindsTo=sy-qdrant.service` cascades a SIGTERM into the knowledge daemon, which never gets past its `qdrant::wait_ready` call.
3. The aiplane NPU embedder lives inside the knowledge daemon process, so no NPU hardware context is opened, and `sy mon`'s NPU sensor sees zero holders.
4. There is no auto-recovery path in `sy`; manual `find / rm` on the corrupt file is the only way out.

## Root Cause
- **Proximate (data):** qdrant performs atomic writes by creating sibling temp directories (`<shard>/.atomicwrite<random>/`) and renaming them into the segment tree. If the process is killed between `create()` and the final fsync/rename of `vector_storage/vectors/config.json`, the file lands on disk as a 0-byte placeholder. Next start, `serde_json` rejects the empty file ("EOF while parsing a value at line 1 column 0"), and the segment loader propagates that as a panic.
- **Proximate (cascade):** `configs/systemd/user/sy-knowledge.service` declares `BindsTo=sy-qdrant.service`, so qdrant's failed state immediately tears knowledge down — there is no chance for the daemon's embedded `spawn_qdrant()` path to take over and run a repair.
- **Distal (sy):** sy treats qdrant's storage tree as opaque. The supervisor has no scrub-on-start step, so any one-segment corruption permanently bricks the knowledge plane until a human notices. CLAUDE.md "no snowflakes" says sy should own this recovery, not document a manual workaround.

## Fix
1. **New module `src/knowledge/repair.rs`:**
   - `pub fn quarantine_corrupt_segments(storage_dir: &Path) -> Result<RepairReport>` walks `<storage>/collections/*/<shard>/segments/<uuid>/`, validates that every `*.json` file is non-empty and parseable, and moves any segment that fails validation to `<shard>/segments.quarantine/<unix-ts>-<uuid>/`. Sweeps stale `.atomicwrite*` directories from each shard root in the same pass. Idempotent (skips `segments.quarantine`, `temp_segments`, and missing dirs); returns a `RepairReport { quarantined: Vec<PathBuf>, swept_atomicwrite: usize, .. }` for structured logging.
2. **CLI surface:** new `sy knowledge repair-qdrant` (with `--json` / `--quiet`) so the systemd unit can call it and operators can run it on demand.
3. **Wired into both supervisor paths:**
   - `src/knowledge/daemon.rs::run()` calls `repair::quarantine_corrupt_segments(&storage)` before `spawn_qdrant()` (covers the non-systemd path).
   - `configs/systemd/user/sy-qdrant.service` gains `ExecStartPre=%h/.local/bin/sy knowledge repair-qdrant --quiet` (covers the systemd-managed path that owns the real production process today).
4. **Hermetic tests:** inline `#[cfg(test)]` in `src/knowledge/repair.rs` builds a fake storage tree with a healthy segment, a segment containing an empty `vector_storage/vectors/config.json`, and several `.atomicwrite*` leaks; calls the repair function; asserts (a) the bad segment moved to `segments.quarantine/`, (b) the healthy segment is untouched, (c) all atomicwrite dirs are gone, (d) re-running is a no-op.
5. **One-shot recovery on this host:** after the code builds, run `sy knowledge repair-qdrant` on the user's data dir, then `systemctl --user reset-failed sy-qdrant.service && systemctl --user start sy.target` to bring knowledge + the NPU embedder back up.

## Traceability
- Failing tests: `src/knowledge/repair.rs::tests::*` (4 cases)
- Fixed in: `src/knowledge/repair.rs` (new), `src/knowledge/mod.rs` (mod + clap), `src/knowledge/daemon.rs` (call before `spawn_qdrant`), `configs/systemd/user/sy-qdrant.service` (`ExecStartPre`).
