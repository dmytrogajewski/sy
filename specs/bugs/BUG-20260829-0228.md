# BUG-20260829-0228: Opaque completion identifier rejected

## Summary

The real pinned SGLang candidate reached HTTP readiness and returned a valid
OpenAI-compatible text completion, but Spark rejected semantic readiness and
terminated the otherwise healthy engine.

## Reproduction

- Serve the installed NVFP4 model with the declarative SGLang engine on the
  real `dgx-spark`.
- Observe HTTP 200 from `POST /v1/completions` followed by
  `semantic completion contract rejected` and a deliberate SIGTERM.
- Replay the immutable container outside the managed lifecycle and send the
  exact semantic probe. The response has the expected object, model, one
  choice, bounded usage, and a 32-character hexadecimal opaque identifier.

## Expected

Semantic readiness accepts a non-empty, bounded identifier composed of safe
wire characters. The OpenAI protocol treats the identifier as opaque and does
not require an engine-specific prefix.

## Actual

The validator accepts only `cmpl-*` and `chatcmpl-*`, encoding response naming
conventions used by two engines into the generic protocol gate.

## Root Cause

`valid_semantic_completion` confuses common example prefixes with a protocol
invariant. SGLang's current completion endpoint exposes its internal request
identifier without either prefix.

## Fix

Validate the identifier as a non-empty, length-bounded safe opaque token while
preserving all model, response-shape, finish-reason, text-size, and token-usage
checks.

## Traceability

- Failing test: `spark::upstream::tests::semantic_contract_accepts_safe_opaque_identifier`
- Real device: pinned SGLang container and installed immutable NVFP4 snapshot
  on `dgx-spark`
