# JOURNEY-20260825-2251: Serve any compatible model with one Spark engine

## Actor & Goal

- Actor: a developer using `sy spark` from a trusted workstation.
- Goal: download an immutable Hugging Face model and serve it on `dgx-spark` without adding a model-specific recipe or rebuilding sy.
- Hardest constraint: keep arbitrary image, mount, network, and command execution impossible while keeping every operational serving value—including context length, environment, and sampling defaults—in editable configuration rather than compiled Rust.

## Happy Path

1. The user runs `sy spark dgx-spark download <owner/model> --revision <revision> --alias <name>` → Spark resolves the revision to an immutable commit, downloads it into the native Hugging Face cache, verifies the snapshot, and records the alias → the user receives one durable model identity.
2. Spark reads the model's verified `config.json` and selects a matching architecture profile from `/etc/sy/spark/engine.toml` → reasoning/tool parser flags remain ordinary editable configuration → no container argument, image, mount, or executable is accepted from the user.
3. The user runs `sy spark dgx-spark serve <name>` → admission checks the verified model record and available unified memory, then the executor constructs a digest-pinned container specification from the installed engine configuration around that exact snapshot → progress reports pull, start, health, and publish phases.
4. The engine passes bounded native, OpenAI Chat/Responses, and Anthropic Messages probes → the gateway publishes the stable authenticated URLs → `sy spark dgx-spark ps` reports the instance healthy.
5. The user runs `sy spark dgx-spark launch codex|claude|opencode --model <name>` → the existing launch adapter reuses the healthy instance and streams tool, reasoning, and text events through the compatible protocol.
6. The user runs `sy spark dgx-spark stop <name>` and later serves it again → only the model process changes; its verified cache, alias, policy, and durable operation history remain available.

## Edge Cases

- **The model is not supported by installed vLLM**: startup or the bounded capability probe fails with the engine error and logs; the route is never published and the model remains downloaded.
- **The model snapshot is missing or has changed**: the executor refuses to construct a mount and asks for a new verified download; it never serves a mutable repository reference.
- **The architecture has no specialized profile**: the declared default profile is used; adding support means editing configuration, not rebuilding sy.
- **Memory admission fails**: the request exits with the existing stable resource refusal and does not stop a healthy instance implicitly.
- **Engine pull or startup is interrupted**: the durable operation becomes failed/cancelled and reconciliation removes only the incomplete generation.
- **A pre-upgrade recipe-backed instance is running**: the upgraded agent continues reporting and stopping it safely; new starts use the generic engine policy, and successful cutover retires the legacy generation.
- **Two starts target the same model**: the existing lease and idempotency rules converge on one generation.
- **The fixed engine image is unavailable**: the operation fails closed; sy never substitutes another tag or updates the DGX OS, driver, firmware, CUDA stack, or Docker daemon.
- **An engine optimization is unstable for an architecture**: the matching declarative profile disables that optimization; Rust and the public API remain model-agnostic.

## Acceptance Criteria

- [x] A model repository absent from sy source/config can be downloaded and served without rebuilding sy.
- [x] New serving has no recipe selection and does not require an unverified override.
- [x] Tests prove users cannot control the engine image, entrypoint, executable, mounts, network mode, or arbitrary argv.
- [x] The vLLM engine is pinned to `vllm/vllm-openai@sha256:ae35bb2db70814d1239ea588e1abb5288adcbd287cac1d4d00ea0f28cd2033df` by configuration identity.
- [x] Engine version, image, arguments, environment, routes, resource and sampling tuning, and architecture profiles exist only in `configs/sy/spark/engine.toml`; a regression test rejects their appearance in production Rust.
- [x] Legacy recipe-backed instances remain observable and stoppable during migration.
- [x] Real `dgx-spark` verification downloads/uses the existing Ornith snapshot, cuts it over to the generic engine, and leaves it healthy.
- [x] Bounded live checks confirm streaming OpenAI Chat, OpenAI Responses reasoning, Anthropic thinking/signatures, and a launched agent.
- [x] `sy spark dgx-spark ls`, `ps`, `show`, `logs`, `serve`, `stop`, and re-serve work end to end after cutover.
- [x] No load, stress, reboot, OS update, driver update, firmware update, or host CUDA update is performed.
- [x] Strict all-target clippy and the complete Spark-enabled test suite pass.
- [x] README and Spark reference describe the engine/model boundary and generic workflow.

## Out of Scope

- Serving model formats or tasks unsupported by vLLM 0.27.1.
- User-provided engine images, shell commands, entrypoints, mounts, ports, Docker flags, or network policy.
- Automatic DGX OS, driver, firmware, CUDA, Docker, or kernel upgrades.
- Benchmark-driven model ranking and stress/load testing.

## Open Questions

- None. The engine is fixed and policy-owned; model identity and bounded capability hints are user-owned data.
