# JOURNEY-20261018-1635: Clear PolicyKit authentication prompts

## Actor & Goal

- Actor: desktop user authorizing an app or agent action.
- Goal: know whether to approve on the phone, touch FIDO, or enter a password.
- Hardest constraint: preserve PolicyKit's identity and PAM authorization checks.

## Happy Path

1. An app requests authorization through PolicyKit.
2. The sy agent opens a themed dialog showing the action and chosen identity.
3. The existing polkit-1 PAM stack includes sudo authentication; the dialog
   explains phone approval and FIDO touch, displaying actual PAM messages.
4. When PAM requests a password, the dialog enables a masked entry and submit.
5. Successful authentication closes the dialog and completes the original request.

## Edge Cases

- Phone unavailable: PAM continues to FIDO/password; the dialog explains the chain.
- Cancellation: close/cancel terminates the helper and resolves the request as cancelled.
- Concurrent requests: serialize or reject clearly, preserving request cookies.
- Wrong password: show failure and permit a fresh request; never grant locally.
- Another agent registered: report registration failure without disrupting it.
- Non-GUI package builds: the producer and UI share the gui feature boundary.

## Acceptance Criteria

- [x] Tests cover PAM prompt mapping, cancellation, and request isolation.
- [x] Live pkexec works with phone authentication through the sy dialog.

## Out of Scope

- Changing which PolicyKit actions require authorization.
- Making the UI grant privileges or decide authentication success itself.
