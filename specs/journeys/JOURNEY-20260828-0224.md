# JOURNEY-20260828-0224: Build Tetris with Flash-Next and FreeToken on Spark

## Actor & Goal

- Actor: A developer launching Claude, Codex, and OpenCode from the workstation against `dgx-spark`.
- Goal: Use Qwen3.8-Flash-Next and then FreeToken to independently create, verify, and run three fresh Tetris implementations per engine.
- Hardest constraint: Models, engine selection, image identity, resources, tuning, routes, and probes remain signed configuration; Rust recognizes only generic schemas and artifact traits.

## Happy Path

1. The operator downloads the configured `qwen3.8:flash-next` alias → the model catalog resolves the exact RadixArk serving set at one immutable revision → `ls` reports the complete installed identity and verified hashes.
2. The operator serves the alias → the executor selects the pinned patched-vLLM image only because the artifact selects its explicit profile → PLE stays mmap-backed on NVMe while QSA and MTP remain native → the cold generation reaches healthy with text, reasoning, tools, and streaming routes published.
3. The operator creates three empty directories under `~/sources/testbed` → each directory contains only a concise Tetris brief → no prior generated code or agent transcript is reused.
4. The operator launches Claude, Codex, and OpenCode separately → each client receives the same model alias through its native compatibility surface → each client creates a playable Tetris game, runs its checks, and exits successfully.
5. The operator runs and inspects all three games → movement, rotation, line clearing, score, game-over, restart, and cursor/input behavior work → the Spark instance remains healthy without an unexpected container restart.
6. The operator installs the pinned FreeToken ARM64 image → the signed generic engine inventory includes `freetoken.toml` without adding an engine name to Rust → dry-run selects it for the compatible safetensors model.
7. The operator downloads and serves Qwen3.6-35B-A3B-NVFP4 → FreeToken starts with fused MoE, Triton kernels, and an explicit KV budget → native Chat, Responses, and Messages streams pass through sy.
8. The operator repeats three new Tetris directories and three independent launches → all clients finish working games → sy records measured performance, resource use, protocol evidence, image/checkpoint fingerprints, and post-run health.
9. The Qwen3.6 35B-A3B run also supplies the large-model qualification → a streamed reasoning/tool request completes inside its declared resource envelope → no second rejected checkpoint is transferred.

## Edge Cases

- **A split GGUF shard is absent or has a different digest**: download/admission fails before container creation and names the exact shard (surfaced via: operation error, stderr, JSON error).
- **The llama.cpp image predates `qwen4exp`**: image/config validation or model load fails closed; no unrelated engine is selected (surfaced via: serve operation and bounded logs).
- **Flash-Next output is incoherent on GB10 CUDA**: semantic and deterministic coding checks fail qualification; a corrected pinned revision or generic CUDA backend setting is evaluated in configuration (surfaced via: response transcript, game build, logs).
- **A configured quant violates the system reserve**: admission or startup stops without OOM recovery loops; a lower-memory quant requires an explicit catalog change (surfaced via: operation error and resource evidence).
- **A client exits before finishing**: that fresh directory is retained as failure evidence and rerun from a new empty directory after the protocol/runtime root cause is fixed (surfaced via: client trace and filesystem).
- **FreeToken chooses offload or automatic KV sizing**: engine argv verification fails because the Spark profile must be fused and explicitly sized (surfaced via: dry-run, container argv, engine log).
- **FreeToken native streaming differs from a client contract**: the route remains available for diagnosis, but qualification fails until named SSE events, reasoning, tools, usage, cancellation, and follow-up all pass (surfaced via: captured streams and client trace).
- **A proposed large MoE exceeds physical memory**: declared artifact and runtime envelopes reject it before start rather than relying on swap or OOM recovery (surfaced via: dry-run/admission error).
- **Any protected appliance component changes**: deployment fails and reports the fingerprint mismatch (surfaced via: signed upgrade report).
